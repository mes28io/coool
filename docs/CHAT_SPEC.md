# coool chat sessions: spec v1

## Why

Today a session started inside coool is a PTY running the CLI's own TUI, shown in xterm.js. The owner does not want new chats to look like a terminal. A chat started in coool must look and behave like the designed Activity view: streamed replies, animated step lists, subagent cards, approval cards, a composer with slash commands and a model picker. Everything Claude Code and Codex can do (slash commands, model switching, context and status, subagents) must be reachable from that native UI. The terminal remains as an escape hatch, not the default.

## Approach

Drive the official CLIs through their structured, non-TUI modes. coool still never touches credentials; the CLI uses whatever login it has.

- **Claude Code:** `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages` (plus `--resume <id>`, `--model`, `--permission-mode`, and the permission-prompt mechanism: see `claude --help` for `--permission-prompts` / `--permission-prompt-tool`; and `--allow-dangerously-skip-permissions`, which turns nothing on but lets a chat started in another mode switch to Bypass later: without it the CLI refuses `set_permission_mode` bypassPermissions, "the session was not launched with --dangerously-skip-permissions"). One long-lived process per chat; user turns are written to stdin as JSON lines; events arrive on stdout. The first `system`/`init` event lists the model, tools, slash commands and agents.
- **Codex:** prefer `codex app-server` (JSON-RPC over stdio; `codex app-server generate-ts` / `generate-json-schema` print the protocol). If that proves unworkable, fall back to `codex exec --json` per turn with `resume`, and say so.

Both are wrapped by one provider-neutral driver in `crates/core`, so frontends never see provider wire formats.

## Core API (`crates/core/src/chat/`)

```rust
pub struct ChatOptions {
    pub provider: Provider,
    pub cwd: String,
    pub resume: Option<String>,          // provider session id to continue
    pub model: Option<String>,
    pub permission_mode: Option<String>, // provider's own names, passed through
    pub account: Option<String>,         // Claude Platform key id (APP_SPEC "Claude Platform"); None: the subscription
}

impl Hub {
    pub fn start_chat(&mut self, opts: ChatOptions) -> Result<usize>;   // chat id, stable for the process
    pub fn chat(&self, id: usize) -> Option<&Chat>;
    pub fn chat_mut(&mut self, id: usize) -> Option<&mut Chat>;
}

impl Chat {
    pub fn send(&mut self, text: &str) -> Result<()>;        // a prompt, or a slash command typed as text
    pub fn interrupt(&mut self) -> Result<()>;               // stop the current turn, keep the chat
    pub fn set_model(&mut self, model: &str) -> Result<()>;
    pub fn set_permission_mode(&mut self, mode: &str) -> Result<()>;
    pub fn respond_permission(&mut self, request_id: &str, allow: bool, always: bool) -> Result<()>;
    pub fn respond_permission_remember(&mut self, request_id: &str, remember: &str) -> Result<()>; // allow + apply one remember option
    pub fn steer(&mut self, text: &str, now: bool) -> Result<String>;   // a note for the running turn -> note id (see "Steering")
    pub fn cancel_steer(&mut self, note_id: &str) -> Result<()>;      // withdraw a note that is still queued
    pub fn stop(&mut self);                                   // end the process
    pub fn events_since(&self, seq: u64) -> (Vec<ChatEvent>, u64); // full history is kept (bounded), so a late UI can replay
    pub fn info(&self) -> ChatInfo;                           // provider, cwd, session_id, model, state, running
}
```

`Hub::refresh` links a chat to its discovered `Session` the way it links PTYs (new additive field `Session.chat: Option<usize>`), so the sidebar shows one row per chat, not two. "Open in terminal" links the new PTY to the chat's session id at once, and an ended chat yields its session to that PTY, so the row reads as one continuous session.

### Events (serde, `#[serde(tag = "type", rename_all = "snake_case")]`)

Every event also carries `seq: u64` and `ts: u64` (epoch ms). This JSON is exactly what the app receives.

| type | fields | meaning |
|---|---|---|
| `ready` | `session_id`, `model`, `cwd`, `permission_mode`, `slash_commands: [{name, description}]`, `models: [{id, label}]`, `agents: [string]`, `context_window: number \| null` | CLI started; drives autocomplete and pickers. May be re-sent when any of it changes. |
| `user_message` | `id`, `text`, `steer: bool`, `note_id: string \| null` | echo of what was sent; `steer: true` (with the note's id) for a steering note the agent took in, shown with its step rather than as a prompt |
| `text_delta` | `message_id`, `text`, `parent_tool_id: string \| null` | streamed assistant text |
| `thinking_delta` | `message_id`, `text`, `parent_tool_id` | streamed reasoning, when the provider exposes it |
| `assistant_message` | `id`, `text`, `model`, `parent_tool_id` | a completed text block (authoritative; replaces deltas) |
| `tool_start` | `id`, `name`, `summary`, `input` (json), `parent_tool_id` | `parent_tool_id` set means it belongs to a subagent launched by that tool call |
| `tool_end` | `id`, `ok: bool`, `output: string` (truncated to ~4k) | |
| `permission_request` | `request_id`, `tool`, `summary`, `input`, `remember: [RememberOption]` | UI must answer with `respond_permission` / `respond_permission_remember`; see "Remember options" |
| `usage` | `model`, `tokens: {input, cached, output, context}`, `context_window: number \| null` | after each model response |
| `state` | `state: "idle" \| "working" \| "waiting_permission"` | |
| `turn_end` | `duration_ms`, `ok: bool` | |
| `cost` | `usd: number` | Claude Platform (APP_SPEC "Claude Platform"): what an API-key chat's turn cost by the CLI's own count (the change in `result.total_cost_usd`); only for chats on an API key |
| `notice` | `level: "info" \| "warn" \| "error"`, `text`, `needs_terminal: bool` | CLI output with no better home, errors, and "this command only works in the terminal" |
| `exited` | `code: number \| null` | process ended |
| `open_failed` | `error`, `reason: "newer_cli" \| "not_found" \| "exited" \| "other"`, `cli_version: string \| null`, `resumed: bool`, `unsent: [{id, text}]` | the conversation couldn't be opened (Codex `initialize` / `thread/start` / `thread/resume` error, or the app-server gone before the thread opened; Claude Code: an error `result` before it answered `initialize` on a `--resume`). Final: the CLI's input is closed so `exited` follows, sends and notes are refused, `unsent` lists the prompts shown as sent that never reached the agent. `newer_cli`: Codex's "failed to deserialize stored thread item … unknown variant" (a newer Codex saved it). The app shows one card (plain reason, the raw error folded, the unsent text with Copy, "New chat in this folder" carrying it as a draft), no `exited` row, and the composer and its chips disabled |
| `question` | `request_id`, `questions: [Question]` | the agent asks the person something; see "Questions" |
| `steer` | `note_id`, `text`, `state: "queued" \| "picked_up" \| "interrupted" \| "unused" \| "cancelled"`, `tool_id: string \| null` | a steering note changed state; see "Steering" |
| `commands` | `commands: [{name, description, argument_hint, aliases, kind}]` | the slash commands with `kind`: `command` (runs in the chat), `skill` (sent to the model) or `terminal` (TUI only). Sent right after `ready` whenever it changes; `ready.slash_commands` stays as it was |

### Remember options ("don't ask again")

coool never invents a rule: what can be remembered is exactly what the CLI offers for that request, put into plain words. `permission_request.remember` lists them, this-chat-only ones first; empty means nothing can be remembered (the UI shows no such action).

```ts
RememberOption = { id: string,            // pass to respond_permission_remember
                   label: string,         // button text: "Allow all edits in this chat", "Always allow `npm test` commands in this project"
                   detail: string,        // what changes and where it is kept
                   scope: "chat" | "project" | "user",   // chat: nothing saved; project/user: written to `file`
                   file: string | null,   // ".claude/settings.local.json" (folder-relative), "~/.codex/rules/default.rules", ...
                   mode: string | null,   // set when it switches the chat's permission mode
                   rules: string[] }      // the CLI's own rule syntax, e.g. "Bash(npm test *)"
```

- **Claude** (`can_use_tool.permission_suggestions`, observed with Claude Code 2.1.325 in a throwaway folder): Write -> `setMode acceptEdits` for the session; Bash `npm test` -> `addRules Bash(npm test *)` to `localSettings`; a compound command -> one rule per part, together; Read outside the folder -> two session rules (the path and its realpath); WebFetch -> `addRules WebFetch(domain:…)` to `localSettings`. Entries with the same destination become one option (they are applied together, as in the CLI's own prompt). Destinations: `session`/`cliArg` = chat, `localSettings` = `.claude/settings.local.json`, `projectSettings` = `.claude/settings.json`, `userSettings` = `~/.claude/settings.json`. For every saved rule the driver adds a this-chat twin first (the same rules with destination `session`), so remembering never requires writing a file. Applying one sends its entries as `updatedPermissions`; a mode switch comes back as a new `ready.permission_mode`.
- **Codex** (`item/commandExecution/requestApproval.availableDecisions`, 0.145): `acceptForSession` = chat; `acceptWithExecpolicyAmendment` = a prefix rule saved to `$CODEX_HOME/rules/default.rules` (every project); `applyNetworkPolicyAmendment` (allow) = a saved network rule. In `untrusted` mode a command offers only the saved prefix rule. File changes (and the legacy requests) have the fixed set `acceptForSession` (+ the amendment when proposed).
- `respond_permission(id, true, true)` (the old "always") applies the first option only if it is this-chat-only, else allows once: a saved rule is applied only through `respond_permission_remember`, from a control that says so.
- UI: the card's second action is the list of options (label + detail; saved ones marked with their file); after one is applied, the timeline note says what changed ("this chat is now in Accept edits mode", "allowing `touch e.txt` in this chat", "… saved to .claude/settings.local.json") and a mode switch flashes the mode chip. ⇧⌘↵ applies the first option when it is this-chat-only.

### Requests of coool's own

coool itself can ask the person in a chat, through the same request UI (the device gate, APP_SPEC "Device permissions"): `ChatHandle::ask(tool, summary, input, remember) -> (request_id, Receiver<ExternalAnswer>)` pushes an ordinary `permission_request` (`request_id` starting `coool-`; for the device gate `input.coool_device = {device, kind, lead, body, note}`) and the chat reads `waiting_permission` until it is answered. The answer goes through the usual calls: `respond_permission(id, allow, always)` (`always` applies the first option only if it is this-chat-only) and `respond_permission_remember(id, option)` resolve it in coool (`Allow`, `Remember(option)`, `Deny`) and never reach the CLI. While such a request waits, the chat's state stays `waiting_permission` even when the CLI reports `working` (the CLI doesn't know about it); the CLI reporting `idle` (the turn ended, Stop, an exit) cancels it (`Cancelled`). `ChatHandle::withdraw(id, note)` takes back one nobody answered (a timeout), with an info `notice`. A remember option of coool's own has `scope: "project"` and `file: "coool (Settings > Devices)"`: saved in coool's data, not in a settings file.

### Questions

When the agent asks the person a question mid-task (Claude's `AskUserQuestion` tool; Codex's `item/tool/requestUserInput`, which codex-cli 0.145 offers only in its plan collaboration mode (`default_mode_request_user_input` is off), so a coool Codex chat, which runs in the default mode, never asks one; Codex has no plan approval either: its plan tool only reports steps), the driver emits `question` instead of `permission_request`, and the chat state is `waiting_permission` until it is answered:

```ts
Question = { id: string, header: string, question: string,
             options: [{label, description}],   // empty: free text only
             multi_select: bool, allow_other: bool /* a typed answer is accepted */, secret: bool }
```

- Answer: `Chat::respond_question(request_id, answers: &[Vec<String>])`: one list per question, in order, holding the picked option labels and/or the typed text. At least one question must have an answer.
- Decline: `respond_permission(request_id, false, false)`.
- Claude wire format (observed with Claude Code 2.1.325): the question arrives as `can_use_tool` for `AskUserQuestion`; the answer is `{"behavior":"allow","updatedInput":{...input, "answers": {"<question text>": "<answer>"}}}`, where several picks are joined with `", "` and a typed answer is passed as is. The model then sees `"<question>"="<answer>"`. A decline is `{"behavior":"deny","message":"The user declined to answer."}`.
- Codex wire format (`codex app-server generate-ts`, experimental in 0.145): the response is `{"answers": {"<question id>": {"answers": [..]}}}`; a decline is an empty `answers` map.
- The UI shows a question card in the timeline (same design language as the approval card), the session counts as "Needs you", and the tool step for the question itself is not listed separately.
- Number keys: each option shows its number (1–9). While the card has focus (a click on it, Tab, or a new card arriving when nothing else has focus), a plain 1–9 picks that option, exactly like a click: it answers a single single-choice question, toggles an option of a multi-select one, and picks for the question holding focus (else the first unanswered one) when there are several. Never while typing: keys in the composer, the "Or type another answer" field or any input stay text, and ⌘/Ctrl/Alt digits are left to the app's shortcuts. The card's hint reads "Press 1–N to answer" while it has focus (`lib/questionKeys.ts`, tested).
- Later: the card's "Later" folds it to one line just above the composer ("Claude has a question · <first question>", `components/QuestionLater.tsx`), so the person can keep reading; the turn stays paused and the session still counts as Needs you. Clicking the line reopens the card in the timeline, scrolled into view and focused (so a number key answers at once). Which questions are set aside is UI state only, never persisted; answering, declining or the turn ending removes the line.

### Risky tag (approval cards)

The approval card can carry a small red "Risky" tag next to the tool name, with the reason on hover, from a fixed rule set (`lib/risk.ts`, `riskOf(tool, input, cwd) -> { risky: true, reason } | null`, tested in `risk.test.ts`; `components/RiskTag.tsx` draws it and is meant for reuse, e.g. the Needs-you page):

- a command (Claude's Bash, Codex's shell, `bash -lc "…"` unwrapped) that deletes recursively and forcibly (`rm -rf` in any spelling), force-pushes (`--force`, `-f`, `--force-with-lease`, `+branch`, `--mirror`), deletes a remote branch, runs `git reset --hard` or `git clean -f…`, pipes a network script into a shell (`curl … | sh`, `sh -c "$(curl …)"`, `bash <(curl …)`), uses `sudo` / `doas` anywhere in a chain, or deploys / publishes (vercel, netlify, fly, firebase, wrangler, kubectl / helm changes, terraform / pulumi apply or destroy, npm / pnpm / yarn / cargo / gem publish, docker push, `git push heroku`, gcloud / aws / az deploys, `aws s3 sync … s3://`, supabase pushes, `gh release create`, app store releases);
- a file write (Write, Edit, MultiEdit, NotebookEdit, Codex's apply_patch) outside the chat's folder. The system temp folders (`/tmp`, `/private/tmp`, `/var/folders`) don't count, and with no known folder the rule says nothing. A Codex patch request carries `{files: [absolute paths, a move's target too], changes: [{path, kind: "add" | "delete" | "update", move_path?, diff}], reason}` (`chat/codex.rs` `patch_input`, from the `fileChange` item that precedes the approval; `lib/patch.ts` reads it): every file and move target is checked. Its card says "Codex wants to create a file / edit a file / change N files" with the paths, and the Needs you page shows each file's change as a word diff (an update per hunk with its context lines, a new file as all new text). A Codex command request in a managed-network prompt carries `network_host` ("Codex wants to reach example.com").

Further rules (each unit-tested with negatives so ordinary commands stay untagged): every simple command of a chain is checked, split at `&&`, `||`, `;`, `|`, `&` outside quotes, and through `bash -c "…"` / `sh -c` / `zsh -lc`, `eval "…"`, `env`, `xargs` (`xargs rm` is itself risky); `rm` / `unlink` of a path outside the chat's folder even without `-rf` (`~`, `$HOME`, `..`, absolute paths; temp folders and `/dev/null` don't count); `find … -delete` / `-exec rm`; `git checkout -- …` / `git checkout .` / `-f`, `git restore <paths>` (unless only `--staged`), `git stash drop|clear`, `git branch -D`; `chmod -R` / `chown -R` / `chgrp -R`; `dd of=`; `mkfs*`, `diskutil erase…`; `> file` overwriting a file outside the chat's folder (not `>>`, not `2>&1`); `DROP TABLE|DATABASE|SCHEMA` / `TRUNCATE` through a database client (psql, mysql, sqlite3, mongosh, …) and `dropdb`; `kubectl delete`, `terraform destroy`, `docker … prune`, `gh repo delete`. The path rules need the chat's folder (`commandRisk(cmd, cwd)`); without one they say nothing.

It is a short, fixed list. Only "Risky" is ever shown, never "safe" (no tag means only that no rule matched, and the request still deserves a read; the tag's tooltip says so). There is no countdown and no default answer: coool never answers a request for the person. coool's own device requests (`coool_device`) carry no tag.

### What this does and why (approval cards and the Needs you page)

Every permission request explains itself, so the person doesn't have to guess from a raw command (`components/Explain.tsx`; pure parts in `lib/explain.ts`, tested in `explain.test.ts`; reads shared per request id in `lib/explainStore.ts`). Not for coool's own device requests, which say what and where themselves, nor for plans (the plan card is the plan).

- **The agent's own claim, always, at once, no model call:** "Claude says · its own words, not checked": the tool call's `description` (also `justification` / `reason` when a tool has one), its last paragraph before asking (else its last reasoning), and the title of a plan approved earlier in the chat. Secrets in it are hidden. For a terminal session coool doesn't drive, the same from the transcript.
- **The AI read, only when AI insights is on:** an independent reading by the insights model (`claude-haiku-5-5`, Settings > AI insights: the same switch, Keychain key `coool-anthropic-api-key` / env `COOOL_ANTHROPIC_API_KEY`, and hourly cap as insights, `Insights::take_slot`; no second key path). Core `crates/core/src/explain.rs`, command `explain_request(req) -> { status: "off" | "limited" | "error" | "done", read: { what, why, check[], mismatch }, model, usd, ms }`. One call per request, cached by request id (answers only; at most 200 kept), 20 s timeout in the backend, and the UI stops waiting after 25 s ("The AI read didn't come back in time."; a later answer still fills in). The card never waits on it: Allow / Deny work the same before, during and after it. Labelled "AI read" with a tooltip naming the model and saying it can be wrong. For a terminal session it runs only when the wait names its command.
  - **Sent to the model, and nothing else:** the tool name; from the request's own input only the fields that say what it does (a command and its description; an edit's file, old and new text; a write's file and content; a URL and what it looks for; a patch (a Codex chat's patch request: each file, what it does to it and its diff, at most six files; a credentials-like file's diff is left out); any other tool's input JSON), each capped (2400 / 1200 characters); the working folder relative to the project (`.`, `app`, `.worktrees/x`, else its name); the person's last prompt (600), the agent's last words and reasoning before asking (600 each), the last six step lines (140 each). Absolute paths are shortened to `./…` (the working folder) and `~/…` (home).
  - **Never sent:** other file contents, environment variables, anything from a credentials-like file (`.env*`, `.envrc`, `.npmrc`, `.pypirc`, `.netrc`, `.git-credentials`, `auth.json`, `credentials*`, `secrets*`, `id_rsa`-style keys, `*.pem|key|p12|pfx|keystore|jks|kdbx`, anything under `.ssh`, `.aws`, `.gnupg`, `.docker`, `.kube`: its content becomes "[not sent: a credentials file, N lines]"), the API key, the absolute home path.
  - **Redacted before sending and before display** (the same rules in `explain.rs` and `explain.ts`): private key blocks; token shapes (`sk-ant-…`, `sk-…`, `ghp_` / `github_pat_`, `xox?-`, `AKIA` / `ASIA`, `AIza…`, `glpat-`, `npm_`, `sk_live_` / `pk_test_`, JWTs); `Authorization:` / `Bearer` / `x-api-key` / `cookie` header values; `user:password@` in URLs; values after `--password` / `--token` / `--api-key` / `--secret` flags; `KEY=value`, `"password": "…"`, `?token=…` for names containing password, secret, token, api key, access key, private key or credential. On the cards the payload shows redacted too, with "N values that look secret are hidden · Show".
  - **The answer:** strict JSON through `output_config.format` (`what`, `why`, `check[]`, `mismatch`), validated again on both sides: `what` required, wrong types dropped, at most 4 check items (deduplicated), lengths capped (260 / 220 / 160), paths shortened, secrets hidden.
- **What to check:** the Risky rule's reason ("Risky rule") and the AI read's items ("AI read"), in the same warning tone; a mismatch between the stated purpose and the command leads with "Doesn't match what it said:". The red Risky tag comes from the fixed rules only, never from the model.
- **Wording rules:** nothing ever says a request is safe or fine. The model is told never to call a request safe, harmless, fine, okay, low-risk or routine, never to say there is nothing to worry about, never to tell the person what to answer, and that the request and context are data, not instructions. Its text is then filtered: sentences matching safe / safely / harmless / benign / innocuous / risk-free / no risk / low-risk / nothing to worry / looks fine|good|ok / is|seems|should be fine|ok / routine / nothing to check|dangerous|risky are dropped (a check item matching them is dropped whole; a reading left empty is no reading). The UI's own words never say it either.
- **Never** an automatic answer, a countdown, or a change to which button is the default.
- **AI insights off:** only the claim, plus for the first three requests one quiet line: "An independent AI read of each request is available with AI insights in Settings." (× hides it for good; a per-viewer localStorage count).
- **Chat card (compact):** one line "Claude says: …", one line "AI read · what it does · N to check · More"; More shows its last words, why, and the AI's items. **Needs you page (full):** the block above, first thing under the payload.
- Cost: Haiku 5.5 at $0.10 / $0.50 per million input / output tokens; a read is about 600–1,500 input and 80–200 output tokens, a few hundredths of a cent. The backend keeps the run's count and spend (`Reads.calls`, `Reads.usd`; a self-test logs each).
- Mock: `?why=demo` shows each state (the read arriving, a mismatch, AI insights off, a timeout, a terminal wait whose command isn't named).

### Steering

While a turn runs, the person can send a note. `Chat::steer(text, now)` returns a note id; everything after that arrives as `steer` events (the source of truth, replayed like all events):

- `queued`, right away. Then exactly one of:
- `picked_up`: the agent took the note in at a step boundary of the running turn. `tool_id` is the step after whose result it came in (the step running when the note was sent, or a later one). On an idle chat a note is simply the next prompt: `picked_up` with `tool_id: null`.
- `interrupted` (`now: true`): the current step was cut and the note started the next turn. `tool_id` is the step that was running when the interrupt went out (`null` if the model was writing text). If the turn ended on its own just before the interrupt landed, the note is `picked_up` with `tool_id: null` instead.
- `unused`: the turn ended (or was stopped) before the agent took the note in. It was **not** sent; the UI offers "Send now" (a normal `send`) / "Discard".
- `cancelled`: withdrawn with `cancel_steer` (additive to the original contract, so a replay does not bring back a discarded note).

A delivered note (`picked_up` / `interrupted`) is also echoed as `user_message` with `steer: true` and its `note_id`, right after its `steer` event. The app shows it there, in the timeline where the agent took it in: a note bubble marked "Picked up mid-turn" or "Interrupted the step" (a prompt bubble when it was delivered as an ordinary prompt). (Until 0.4.7 it showed only as a row under its step, hidden once the steps folded and never drawn under a subagent's step, so a delivered note left the strip and was nowhere on screen.) While a permission request or question is pending, notes wait until it is answered (a `now` note then acts like `now: false`: the step is the one waiting for the person, so nothing is cut). Stop (`interrupt`) leaves every undelivered note `unused`. A note the backend refuses (the chat ended, a restart took longer than its wait) stays in the strip as unused, with Send now / Discard; Now on a queued note withdraws it and sends it again with `now: true` (if the agent took it in meanwhile, the withdrawal fails and it stays delivered).

What "next step" truly means, per CLI (observed with Claude Code 2.1.325 and codex-cli 0.145, `sleep 3` steps, haiku / gpt-5.6-luna):

- **Claude Code.** A user line written to stdin mid-turn is queued by the CLI and taken into the *same* turn after the next tool result (`command_lifecycle` `started` arrives right after that `tool_result`; the model sees "The user sent a new message while you were working"; the transcript records a `queued_command` attachment and `queue-operation remove reason:absorbed_mid_turn`; the turn's `result.user_message_uuids` lists it and it gets no `result` of its own). A line still queued when the turn ends is run by the CLI as a turn of its own immediately after the `result`, too fast to withdraw. So coool holds a note itself until a main-thread step is in flight (a `tool_use` without its result) and only then writes it (with `uuid` = note id): it is taken in after that step. A turn that ends without another step leaves the held note `unused`. `cancel_steer` on a note the CLI holds sends `control_request` `cancel_async_message` (answer `{cancelled}` and a `cancelled` lifecycle frame); once taken in it fails. `now: true` sends `interrupt` (answered at once, `{still_queued: [...]}`) and, as soon as it is answered, writes the note with `priority: "now"`; the cut turn's `result` (`error_during_execution`, after a "[Request interrupted by user for tool use]" line) follows and the note's turn starts right after it. (`priority: "now"` alone does not cut the running tool: it lets it finish and then restarts the turn; with the interrupt it only puts the note first in the CLI's queue.) Notes sent between the interrupt's answer and the cut turn's end go right behind it, also with `priority: "now"` (a second `now` note is no second interrupt). A refused interrupt makes the held notes ordinary ones (the next turn, if the turn is over already).
- **Claude Code, background tasks** (observed with 2.1.330, Haiku 5.5, a `run_in_background` `sleep 3` and foreground `sleep 8` steps; `cargo test -p coool-core --test chat_live live_claude_steer_background -- --ignored`). A background command or subagent that finishes queues a task notification in the CLI (`system` `task_notification`). Mid-turn it is taken in after the next tool result like a note (transcript: `queue-operation remove reason:absorbed_mid_turn` and a `queued_command` attachment, not a user entry). Still queued when a turn ends (or is cut), the CLI runs it as a turn of its own: `system/init` with no `command_lifecycle` frame before it, a reply, and a `result` with no `user_message_uuids`. Two consequences coool handles: (1) a `now` note written only after the cut turn's `result` (as until 0.4.7) came after that notification in the CLI's queue, so the agent first answered the notification ("I stopped after step 1. The background command finished…") as if the note had never been sent, and only then the note; with `priority: "now"` at the interrupt's answer the note runs first and the notification's turn after it. (2) Such a turn is the chat working: an `init` while no turn is live, once the CLI has shown lifecycle frames, starts one (`working`), and its `result` lists none of coool's lines, so nothing coool wrote counts as answered by it (until 0.4.7 the oldest line was taken for answered: a `now` note still in the CLI's queue was dropped from the chat's count, the chat showed idle while the CLI still had it, and the next Now went out as a plain prompt behind that turn). Notes wait for its steps, Now and Stop cut it. Residual race: a note written while a very short step finishes can miss that step's boundary; if no further step follows, the CLI runs it as its own turn: reported `picked_up` with `tool_id: null`.
- **Codex.** `turn/steer {threadId, input, expectedTurnId, clientUserMessageId}` is accepted at once (`{turnId}`) and the input is taken in at the next model request, after the running command's output; delivery is the `item/started` `userMessage` whose `clientId` is the note id. A steer that arrives while the agent writes its final answer extends the turn (the agent answers it), so an accepted steer is always delivered. A rejected one (the turn just ended; `activeTurnNotSteerable` during review/compact) ends `unused` with a notice. Codex has **no way to withdraw** a steer: `cancel_steer` works only while coool still holds the note (a pending approval, or before the turn has an id) and fails afterwards. `now: true` sends `turn/interrupt` (the turn ends `interrupted` at once) and starts the next turn with the note (`turn/start` with `clientUserMessageId`).

Tauri: `chat_steer({id, text, now, attachments?}) -> string` (note id), `chat_steer_cancel({id, noteId})`. Re-check with `cargo test -p coool-core --test chat_live live_claude_steer live_codex_steer -- --ignored` (fixtures `claude_steer.jsonl`, `codex_steer.jsonl`). Self-test: `app/scripts/steer-e2e.sh` (scenario `steer-queue`, inside coool and in a chat host, with the stand-in CLI in queue mode, which models the queue, lifecycle frames, background tasks' own turns, `interrupt` and `cancel_async_message` as above): Now with a notification waiting, Now during a turn the CLI runs itself, a note after a subagent step, Now from the strip on a note the CLI holds, Now while text streams, two Now notes, a note queued across a Restart.

### Plans and task lists

Both arrive as ordinary `tool_start` / `tool_end` pairs.

- **Codex** plan tool: every `turn/plan/updated` becomes one pair named `update_plan` (id `plan-<turn>-<n>`), `input: {plan: [{step, status}], explanation?}` with `status` `pending | in_progress | completed` (Codex's `inProgress` mapped). The whole plan each time; there is no plan item in the turn, so nothing is shown twice. (Codex's `plan` thread item, a plan-mode proposal, is not shown.)
- **Claude** task list: Claude Code 2.1.325 offers `TaskCreate` / `TaskUpdate` / `TaskGet` / `TaskList` (deferred, loaded through `ToolSearch`), not `TodoWrite` (only with `CLAUDE_CODE_ENABLE_TASKS=0`), and only on older models (e.g. `claude-haiku-4-5`, the 4.x Sonnet/Opus) or with `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`: on current models (Haiku 5.5, ...) there is no task tool at all. Observed: `TaskCreate {subject, description, activeForm}` -> result "Task #1 created successfully: …", `tool_use_result.task.id = "1"`; `TaskUpdate {taskId, status}` (`pending | in_progress | completed`, `deleted`) -> `tool_use_result.statusChange {from, to}`. The driver keeps the list and, after each successful call, adds a synthetic pair named `TodoWrite` (id `<call id>:todos`) with `input: {todos: [{content /* subject */, status, activeForm}], _synthetic: true}`, the whole current list. The raw `Task*` steps still flow.
- **Claude plan mode** (`--permission-mode plan`): when the plan is ready, `permission_request` for `ExitPlanMode` with `input: {plan /* markdown */, planFilePath /* ~/.claude/plans/<name>.md, written by the CLI */}` (the remember list is empty). Allow: the tool result says "User has approved your plan…", the CLI switches to `default` mode (a new `ready` with `permission_mode: "default"`, not `acceptEdits`) and the same turn goes on to work. Deny: the driver answers "did not approve this plan yet and wants to keep planning…" (the plain denial made the agent stop: "You declined the plan, so I've stopped there"); the mode stays `plan`, and the agent revises or asks. Fixtures: `claude_tasks.jsonl`, `claude_plan_mode.jsonl`, `codex_plan.jsonl`.

### Slash commands

The composer offers `ready.slash_commands` as autocomplete. A command is sent as plain text through `send`. What the structured mode executes shows up as normal events. For commands that have a native equivalent, the app handles them itself and never sends them: `/model` opens the model picker (`set_model`), `/clear` starts a fresh chat in the same folder, `/context`, `/status`, `/cost` and `/usage` open a native panel fed by `usage`, `ready` and the session's token data. For a command that only works in the interactive TUI (login, config screens and the like), the driver emits `notice` with `needs_terminal: true` and the UI offers "Open in terminal", which opens the same session in a PTY via resume.

### Restart

Both CLIs read their settings, MCP config, permissions and instructions (CLAUDE.md, AGENTS.md) only at start, so agents ask the person to "restart Claude Code, then type continue". In coool that is one action: the chat header's Restart button, Restart in the session's right-click menu (sidebar row, header title), ⌘K "Restart this chat", `/restart` in the composer (`/restart continue` sends "continue" once the CLI is back), and "Restart and continue" under an agent's last reply when it asks for a restart (`app/src/lib/restartRules.ts`: plain phrases only, "restart Claude Code / claude / Codex / the session", "relaunch"; not negated, not in code). While a turn runs it asks first ("Claude is working. Restart anyway? The current step is stopped.").

`chat_restart(id, message?)` (`Hub::restart_chat_in`): the CLI is stopped (SIGKILL after the grace), then started again with the chat's own options, resuming its session (`--resume <id>` / `thread/resume`), the model and mode as they are now (Claude Code's mode as it last reported it; a Codex sandbox mode switched mid-chat applies again), the same MCP servers and Ladder, **in the same chat**: the same id, its events numbered on (`exited`, then `restarted` and a notice, then `ready`), so its tab, pane and history stay; the app drops the "process has ended" line on `restarted`. A hosted chat restarts in its host (`Call::Restart`, same key) while "Keep chats running when coool quits" is on; with it off, or a host from before restarts, the app stops it in the host and starts it inside coool, and says so. A restart applies to that chat only: its Ladder helpers keep running (`Hub::is_restarting`). Each start of the CLI has an epoch (`Shared::epoch`): an earlier start's threads and `Chat` leave the new one alone. The coool context tells agents to say "press Restart (or type /restart continue)" instead of "restart Claude Code". The app's event pump reads the old CLI's `exited` and the `restarted` after it as one (they usually arrive in one batch, always for a hosted chat): an `exited` followed by `restarted` is no end, and an ended chat is read again once it runs. A call to a chat being restarted (a message typed meanwhile) waits for the new CLI (up to 20 s) instead of reaching the ended one; a hosted chat taken over by this process stops hearing from its host. Self-test: `app/scripts/restart-e2e.sh` (scenario `restart`; its last step holds the pump so the exit and restart always arrive together, with subagents streaming).

## Models used (monitoring)

Additive fields, filled by the transcript adapters for every discovered session, so they work for sessions started anywhere:

```rust
pub struct ModelUse { pub model: String, pub input: u64, pub cached: u64, pub output: u64, pub messages: u64 }
// Session.models: Vec<ModelUse>   (most used first; includes models used by its subagents, flagged)
// Agent.model: String, Agent.models: Vec<ModelUse>
```

`ModelUse` gets `pub via_agent: bool` when aggregated up from subagents is needed; simplest correct shape wins. The UI shows, per session and per subagent, which models ran and how many tokens each took.

### Context map

Below the models, the Models panel shows what fills the context window: a squarified treemap of the latest request's context, tiles sized by tokens and tinted by kind, the free room hatched (drawn at most 45% of the area, so a 1M window doesn't shrink the parts to slivers; its card says so). Header: "Context", a Main / subagent picker (each subagent has its own context; picking one shows its map, from its own transcript), used / window, and the percent in the same tones as the context ring (warning from 75%, error at 100%). Tiles animate to their new size and position as the numbers change (none under Reduce motion); labels shrink, then hide, on small tiles; every tile has a hover / focus card (what it is, tokens, share of what is in use and of the window, how the number is known, the path for files). While the CLI compacts, the conversation and tool tiles breathe and a "Compacting the conversation…" line shows (chats: the `compacting` event below; other sessions: a `current` starting "Compacting"); afterwards a quiet "Compacted 19:40 · 187k → 54k" line with "Show before" / "Show now", which morphs the map between the two.

Tints (styles.css `--ctx-*`, light and dark): five hue families plus neutral, checked for colour-vision separation: setup (system prompt, tool definitions, reminders) neutral, memory and skills violet, files and images blue, prompts / replies / thinking rose, tool results and sub-agent results orange, a compaction summary green. Labels always carry identity; colour never does alone.

**Command:** `context_map({provider, sessionId, agentId?, cwd?}) -> ContextMap` (`crates/core/src/context.rs`):

```rust
pub struct ContextMap { pub total: u64, pub parts: Vec<Part>, pub compaction: Option<Compaction>, pub note: Option<String>, pub chars_per_token: Option<f64> }
pub struct Part { pub id: String, pub kind: PartKind, pub label: String, pub tokens: u64, pub count: u32, pub path: Option<String>, pub basis: Basis }
// kind: system | tools | memory | skills | file | chat | thinking | tool | agent | image | summary | other
// basis: calibrated | estimated | remainder
pub struct Compaction { pub before: u64, pub after: u64, pub at: Option<u64>, pub auto: bool, pub before_parts: Vec<Part> }
```

Cost: the map is computed only for the transcript whose panel is open, asked for again when the session's context changes (coalesced to one call per ~400ms). The backend keeps the last four asked-for transcripts warm and reads each incrementally from where it stopped; the first read of a transcript byte-scans it for compaction boundaries (no JSON parsing) and parses only from the second-to-last boundary on (one segment for the map, one for its "before"). It never runs in the session refresh: the loader's cheap scan / full load are untouched. On this machine's largest transcripts (150-300 MB) the first read takes 60-120 ms, later ones only the appended bytes.

**Where the numbers come from.** No CLI reports a breakdown, only each request's size. The map divides exactly that size, never invents another:

- **Total**: the latest request's context, the same figure as `Tokens.context` (Claude: the assistant record's `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`, once per message id; Codex: `token_count.last_token_usage.input_tokens`). The parts always sum to it exactly (largest-remainder rounding).
- **Per-step calibration**: between two requests the context grows by `D = ctx[r] - ctx[r-1]`. The previous response's output (`output_tokens`, exact) is split over that response's blocks (text, tool calls, thinking) by estimated size; thinking the transcript leaves out (Claude's display-omitted thinking, Codex's encrypted reasoning) takes what the logged blocks don't explain. The rest, `D - output`, is what came in on the input side (tool results, prompts, attachments) and is split over those items by estimated size. Basis: `calibrated`.
- **Estimated size**: text length divided by a characters-per-token ratio: prose (memory, skills, prompts, summaries, system prompt) 3.8, tool schemas 3.2, tool output and files the transcript's own ratio, learned from steps that hold only tool output (characters / real tokens, typically 2.3-3.3; 3.0 until learned). Images count ~w×h/750 tokens (PNG size read from the header; else 1,600). Within a calibrated step these only set proportions.
- **Steps that don't add up**: if the input side grew far more than its text explains (under 1.2 characters per token), the items keep their estimate and the rest is **"Not in the transcript"** (reminders, hook output the CLI injected without logging). If the context shrank (the CLI cleared old thinking or tool results), the new items keep their estimate and the difference comes off thinking first, then tool results, then the rest. Basis: `estimated`.
- **The first request of a segment** (the session, or since the latest compaction) has nothing to diff against. What the transcript logged before it (the first prompt; Claude Code's attachments: CLAUDE.md `instructions`, `skill_listing`, `invoked_skills`, tool / MCP deltas, `@`-mentioned files; a compaction summary; Codex's developer messages, AGENTS.md, `additional_tools`, a compaction's replacement history) plus the evidence of what it never logs is sized by length: the system prompt and the non-deferred tool list when Claude Code logs them (`api-request-shape`, `prompt_snapshot`) or Codex's `session_meta.base_instructions`; the CLAUDE.md files on disk (user, and each folder from the session's up to home) when the transcript logs no memory. If those add up to more than the first request, all shrink alike. What they don't explain is the **remainder**: "System and tools" when there is no evidence, else "Other system context" (basis `remainder`). Logged items and evidence here are `estimated`.
- **Attribution**: each tool call and its result go to one part: `Read` / `Write` / `Edit` / `NotebookEdit` / Codex `apply_patch` to the file's path (and a shell command that is only `cat` / `sed -n` / `head` / `tail` / `nl` of one file); `Grep` / `Glob` to Searches; `Bash` / Codex `exec` to Test runs when the command runs tests (cargo test, pnpm test, pytest, vitest, jest...; not `test -f`), else Shell; `mcp__<server>__*` to "MCP · server"; `Agent` / `Task` / Codex agent tools to Sub-agents; `WebFetch` / `WebSearch` to Web; `ToolSearch` to Tool definitions; `Skill` to Skills; others to Other tools. `count` is the number of calls ("Test runs ×20"). Files: the six largest on their own, the rest merged into "N other files". Prompts and replies are Conversation; thinking is Thinking; `isMeta` / system-reminder text is Reminders.
- **Compaction**: Claude Code writes a `system` record with `subtype: "compact_boundary"` (`compactMetadata.trigger`, `preTokens`, `postTokens`, `preservedMessages.uuids`) and then the summary as a `user` record with `isCompactSummary: true`; Codex writes a `compacted` record whose `replacement_history` is the new history (its summary an encrypted `compaction` item). Only what follows the latest boundary counts; preserved messages (Claude) are counted again from their remembered sizes. `before` is Claude's `preTokens` (Codex: the last request before); `after` is the first request after it, the same figure the session's context shows (until that request, Claude's `postTokens`, which leaves out the system prompt and tools: a small chat measured 29.3k → postTokens 7.9k, then 29.1k on its next request); `before_parts` is the map just before. Until the first request after a compaction, the map stays the last one before it (the session's context figure hasn't moved either) with a note. Live chats also emit `ChatEvent` `{type: "compacting", active}` (Claude stream-json `system/status` `"compacting"` until the boundary; Codex `contextCompaction` item started / completed).
- **Codex**: the same where the rollout allows (it logs every input and output item; outputs and the call's result come before their `token_count`, so a result whose call is still uncounted goes to the next step). A rollout without per-request usage gets only its total and the note "This rollout reports no per-request usage, so only the total is known."

Checking it: `cargo run --release -p coool-core --example context_print -- [--kinds] <claude|codex> <transcript>...` prints a map and whether its total equals what the session list shows.

## App behaviour

- **New session** opens a chat, not a terminal. Resuming an ended session opens a chat too. "Open in terminal" is a secondary action on any coool-run session.
- **Session view for a chat:** the Activity timeline rendered from chat events (live, streamed), not from the transcript poll. Text streams with a caret; tool calls form the animated step list; subagent work nests under its launching step; permission requests appear as an inline approval card (Allow once / Deny, and the CLI's remember options spelled out; see "Remember options") and the session shows "Needs you" everywhere (sidebar, tab, Mission control).
- **While you were away** (`AwayCard` in `components/Away.tsx`, rules in `lib/away.ts`; the absence is the store's `away[sessionKey]`, see APP_SPEC "Mission control"): when the person comes back to a chat after 5 minutes or more off screen and something worth saying happened meanwhile (a turn failed, the CLI exited with an error, something was committed, pushed, merged, deployed, published or migrated, or two or more turns finished), a card sits in the timeline before the first block from after they left, and the timeline opens scrolled to it (the jump button then points to the rest). One finished turn with edits only is routine: no card, its reply is right there.
  - Header "While you were away · 2h 14m", dot counts (failed in red, done in green, as `Ticker`s) and **Got it**. Rows (36px, at most 5, then "+N more"): failed turns with the prompt, the turn's last error line and **Retry** (resends the prompt, when the chat is idle), then "The CLI exited with code N", then "Finished *prompt* · 4m · 3 files · committed · pushed". A row scrolls to that turn and folds the card.
  - Never shows what waits on the person (the approval or question card at the bottom does) and never counts it.
  - Got it (or opening a row) folds it, 180 ms height and opacity, into a one-line divider "Away 2h 14m · 3 done · 1 failed" that stays for the rest of the visit. It fades and rises 6 px once when it first shows; reduced motion makes both instant. Not part of the transcript: never copied or exported.
  - Sessions read from a transcript have no turn ends, so they get no card; their changes and status count in Mission control's strip.
- **Composer:** multi-line; Enter sends; `/` opens the command menu (fuzzy, keyboard-driven, descriptions shown); a model chip opens the model picker; a permission-mode chip; Stop while working (calls `interrupt`). Up-arrow recalls previous prompts.
- **Header / inspector:** model in use, context meter against the real `context_window` when known (fall back per model family, never a blanket 200k), tokens, and a "Models" breakdown listing each model used by the session and by each subagent.
- Titles: a session without a real title shows a short form of its prompt (first sentence, cut at a clause or word, ~56 characters), or the AI insight headline when insights are on; never the whole prompt.
- Sessions running outside coool are unchanged: read-only Activity from the transcript, with Stop and (once ended) Resume here.
- A stopped or exited Codex chat's session ends at once (`hub.rs`): Codex rollouts carry no pid, so the transcript alone would keep it "idle" for two minutes (or "busy" for ten after a Stop mid-turn) with no Resume; coool ran its only process. It stays ended unless the rollout is written again (a `codex resume` elsewhere).
- Read-only Activity text: each `session.activity[]` / `agent.activity[]` entry has `text` (one line, ~400 columns: lists, TUI, insights) and, for prompts, replies and errors whose one-line form loses anything, `full` (the whole text with line breaks, up to 24,000 characters). Render `full ?? text`. `shortened: true` means what is kept is not the whole message (cut at 24k, or an entry older than the newest 50 full texts of that timeline, which keeps only its one line): say so. Both fields are left out when empty/false. Messages typed mid-turn in Claude Code (`queued_command` attachments) appear as prompts.

### Voice in the composer

The composer is a voice target (APP_SPEC "Voice"): hold Right ⌥ (or ⌥Space hands-free, or the mic chip) to dictate; the listening strip sits at the top of the composer card, the text is inserted at the caret through the textarea's own undo history, and nothing is sent unless "Send when I release" is on (then it goes through the same `send` as Enter, so steering, slash commands and the pending-request guard apply). The fixer's underlines are a mirror layer behind the textarea (no contenteditable); Tab accepts a suggestion only while the slash menu is closed; Esc while listening cancels the dictation and never interrupts the turn. On send, the composer hands the sent text to voice's learning (`noteSent`), which compares it with what was dictated; nothing else about sending changes.

### Long timelines

Both timelines (a chat's, `components/Chat.tsx`, and a transcript session's, `components/Activity.tsx`) draw only the
rows near the view (`components/Windowed.tsx`): the rows within about a screen (at least 900 px) above and below what
is shown are in the DOM, the rest are two spacers whose heights come from each row's measured height, cached per row
key (an estimate by row kind until a row has been drawn once). A chat at its 1,500-item cap has ~670 rows and ~15-30
drawn; a streamed batch costs the same at 120 items as at 1,500.

- **What is read stays put.** WebKit has no CSS scroll anchoring, so the timeline keeps its own anchor: the first drawn
  row that starts inside the view. After every render and every measured change (a row drawn for the first time, a
  step group opening, the cap dropping the oldest rows, older history loading, a pane resize, a card folding above),
  the view moves by however far that row moved. A scroll made by something else (a jump, a card's own
  `scrollIntoView`) is taken as the new place, never undone.
- **Pinned to the bottom** (within 80 px, as before): the drawn rows are the last ones and the view follows the bottom
  as they grow. Scrolled up, new output never moves the view and the jump button says "New" (from the chat's items
  changing, not from the column's height, which drawing rows changes too).
- **Always drawn, wherever they are:** the request waiting for an answer (approval or question card), a subagent card
  asked for (`focusAgent`: sidebar, header chip, Agents panel, Mission control), an unread away card. Each sits in place
  between spacers, so it can be scrolled to like any element.
- **Jumps:** a checkpoint, an away-card row or an asked-for subagent card more than a screen from the view is drawn
  first, then jumped to (no glide over rows that aren't drawn); within the drawn rows it glides as before. The jump
  button glides when the bottom rows are drawn, else jumps. The Later line's card, far away, is jumped to as well.
- **State a row keeps when it is dropped and drawn again** (`useKept`, per timeline, for the app run): a step group's
  open/closed choice, a tool's opened output, a reasoning block, a long notice, a turn's waterfall. Subagent cards keep
  theirs as before (`lib/cardFold.ts`). A row drawn again never plays its entrance; a row that arrived while outside
  the drawn window doesn't either.
- **Selection and copy** work across the drawn rows (a screen above and below the view); text further away is not in
  the DOM, so a selection can't reach it, and a WebKit find (there is no ⌘F in chats) only sees drawn rows.
- Row entrances are a CSS one-off (`.row-in`: 320 ms fade and 10 px rise, the fade only under Reduce motion), not a
  script animation per frame.

### Tool rows

One function names every tool call on every surface (`app/src/lib/toolNames.ts`, `toolRow` / `toolRowFromText`): the chat's step rows and group chips, subagent and Jobs cards, Mission control's "doing now" line and fan-out hover, the Needs-you list and `chatNeeds` (the sidebar and tab "Approve …" line), the read-only Activity timeline and its live row.

- **Built-ins** keep their name and detail ("Bash pnpm test", "Read src/a.ts"). Codex chats name their steps `shell`, `apply_patch` (detail: the files), `web_search`, `spawn_agent` / `wait_agent` / `send_input` / `close_agent` (the app-server's camelCase collab tools mapped to the rollout's names). Codex rollouts (sessions outside coool): codex-cli 0.145 runs in code mode by default and logs every call as one `exec` custom tool whose input is a short script (`const r = await tools.exec_command({cmd:"ls",…}); text(r.output);`); the core reads the first `tools.<name>(…)` call in it as the step (`exec_command · ls`, `apply_patch · ~/w/a.rs, ~/w/b.rs`, `spawn_agent · <message>`; `crates/core/src/codex.rs` `code_mode_call`, also used by the context map), and an apply_patch line names the files it writes, which Mission control's ledger reads one row per file.
- **MCP names** are parsed from both spellings: Claude `mcp__<server>__<tool>`, Codex `<server>.<tool>` (the tool may hold dots).
- **coool-device** tools read as verb phrases, from the input and, once the call ended, the first line of its result: "Opened affectui.com/components" (host and path, the path cut from the middle), `Clicked "Decline"` (the label from `clicked button "Decline" at …`; while running "Clicking #12"), `Typed into "Email" · "a@b.c"`, "Scrolled down", "Took a screenshot", "Read the page …", "Did 3 steps on the page click, type, wait", iPhone ("Tapped", "Pressed Home", "Read the screen") and Mac ("Clicked", "Opened TextEdit", "Ran on the Mac …") equivalents, "Pilot · iPhone <goal>". Failed calls say "Couldn't click #12" in the quiet red row; a wait that timed out is neutral grey ("Waited 5 s page kept changing") and is not counted as failed.
- **Secrets:** typed text is shown only when the result says the field was not hidden and its name doesn't look like a password, passcode, PIN, token or key; otherwise only its length ("21 characters, hidden"). A running type call never shows its text, and a transcript line (whose summary is the typed text itself) never does. Generic tools never show an argument whose name looks secret, and a tool driven by `action` shows the action, not its `text`.
- **Other servers** read "<server> · <Tool in words>" plus the most telling argument (url, query, path, command, name, title…): "github · Create pull request Fix the crash", "Claude Docs · Batch". The server name drops `claude_ai_`, a connector uuid reads "connector", it is clipped to 16 characters; a trailing `_mcp` on the tool is dropped. The raw name is the row's tooltip.
- **Chips** count by group: "Browser ×13", "iPhone ×4", "Mac", "Pilot", the server, or the built-in name. Icons: globe, phone, laptop, bolt (pilot), plug (other servers).
- **Permissions** read in the base form: "Approve Browser: open affectui.com/components"; the approval card and its answered line too ("Denied weather · Get forecast Paris", never `mcp__weather__get_forecast`).
- **ToolSearch** names the tools it loads the same way ("Browser navigate, Browser click, weather · Get forecast", not `select:mcp__coool-device__browser_navigate,…`). `pilot_run` names its target: iPhone, Browser or Mac.

### Where the turn went

Under a finished turn's "Worked for …" (`app/src/lib/turnBreakdown.ts`, `components/TurnBreakdown.tsx`), coool chats only (transcripts have no end times, nothing is guessed):

- **The bar:** 4 px, one segment per kind, in order Thinking, Reading, Editing, Commands, Web and devices, Sub-agents, Other tools, Waiting for you, Writing. Every instant of the turn (`turn.ts - durationMs` → `turn.ts`) goes to one kind: waiting for the person (permission and question items, `ts` → `answeredTs`, and AskUserQuestion / ExitPlanMode spans) first, then a running subagent, then the main thread's tool by kind, then thinking; the rest is Writing. Neutral tints; waiting is `--status-needs` at 60%, sub-agents a faint running blue. Hovering a segment: "Commands · 2m 41s · 7 calls · slowest Bash pnpm test 1m 58s". Hidden for turns under 1 s or with only writing.
- **The waterfall** (click the footer): one row per call on a shared axis, the label from "Tool rows", the call's own time (its span minus any wait for the person inside it), "slowest" on the slowest call (never a subagent's own span or a question); subagent rows fold their calls.
- **Queueing:** calls issued in one message arrive together and the CLI runs them one after another, so a later call's `endTs - ts` includes its wait. Each call's start is moved to when the previous call of its thread (main, or the subagent that made it) ended; runs of read-only built-ins (Read, Grep, Glob, web fetch/search) and subagents run side by side and are not moved. The `tool_start` event carries no message id, so this works per thread rather than per message: a call that started after the previous one ended is unaffected either way.
- **Live:** while a turn runs the same bar sits under the live row and grows each second; the newest segment breathes (static with reduced motion).

### Sub-agent cards

Jobs panel cards and the chat's (and Activity's) subagent cards show, under the title, a 2 px context bar with "32k / ~1M" (`components/AgentFill.tsx`, `lib/agentFill.ts`): the used number is Claude Code's count for the agent (`agent_total` for chats, `tokens.total` for transcript subagents, `tokens.context` for child jobs), the window `contextWindow(model)` with "~" when it is the family's estimate. Blue while running, grey when finished, `--status-needs-text` above 80%; the width springs (`softSpring`) and the number ticks. Hidden when nothing is known (Codex subagents, a subagent before its first response). A Codex chat's `spawn_agent` call returns as soon as the agent starts, so its card stays running until that agent's turn ends (`turn/completed` on its thread; the chat's own turn end or exit closes any still open), and the agent's steps nest under the spawn, never under a later `wait_agent` that names the same agent. In a Codex session's agent list, a subagent counts as running only while its rollout is mid-turn (an idle one is not running). Below it, "↳ from lead: <first line of the Task prompt>" (a transcript subagent's or a job's first prompt), one line, the whole prompt in the tooltip, left out when it only repeats the title.

The browser mock shows all three with `?tools=demo` (one finished turn driving the Browser, iPhone and Mac, then a live one; `&live=0` for none).

### Attachments

The composer takes images and files by paste (a screenshot, files copied in Finder), by drop on the chat (the window's drag-drop events give paths; the chat under the pointer gets them and shows a drop veil) and by the attach button (the system file picker). Up to 10 per message; each shows in the tray above the text as a thumbnail or a chip (type badge, name, size), with a spinner while it is read and a plain reason when refused (too large, too many, already attached, a folder, gone). Rules: `lib/attachRules.ts`; state: `lib/attach.ts`; screens: `components/Attachments.tsx`; core: `crates/core/src/attach.rs`.

What each CLI gets: images (PNG, JPEG, GIF, WebP; larger than 3.75 MB scaled down with `sips`) as real image input: Claude Code a base64 `image` content block before the text, Codex a `localImage` input (coool's stored copy). Every attachment, images too, is named in the text by a line `<attachment kind="file" name="…" type="…" size="…" path="…"/>`, so the agent has the path and reads non-image files itself; HEIC, TIFF, BMP and SVG go as files, and the chip says so. A pasted file without a path is kept in coool's store (`~/Library/Application Support/coool/attachments`, `COOOL_ATTACH_DIR` overrides) and given by that path. While a turn runs, attachments go with the steering note, whole: both CLIs take a full message mid-turn (Claude: one user line of content blocks; Codex: `turn/steer` with the same input list as `turn/start`), so the strip says "goes in at the next step"; only the fallback without `chat_steer` holds the note and its attachments and sends them as the next message ("sends when this turn ends"). `steer` events and the note's `user_message` echo carry `attachments`; a note taken in as Claude's `queued_command` is read back with its images.

`user_message` carries `attachments` (the text without the marker lines). Reading a transcript, the marker lines and the message's images (Claude `image` blocks, Codex `input_image` data URLs, a terminal paste included) become the prompt's `attachments`, so a reopened chat shows them again. Images load by key (`attach_image`): from the store, else from that session's transcript, never from a path. Click: an image opens the lightbox (fit / 100 %, zoom with ⌘-scroll or + / −, ← / → between the message's images, Esc); a file opens the quick look (text with line numbers and colour, a PDF as its first 12 pages drawn to PNG by the app with Quartz, so the page never loads the PDF and nothing in it runs, else Reveal in Finder). Image paths an agent names in a step, inside the chat's folder, get a preview button: read only when clicked, only if the path still resolves inside that folder (symlinks followed first) and only if its bytes are a PNG, JPEG, GIF or WebP. The phone (Remote) gets attachment names only. Browser demo: `?attach=demo` (`lightbox`, `file`, `pdf`, `drop`).

## Tauri contract additions

Commands: `start_chat({opts}) -> number`, `chat_send({id, text, attachments?})`, `attach_paths({paths}) -> [{path, name, attachment?, error?}]`, `attach_bytes({name, data}) -> attachment`, `attach_image({key, provider?, session?}) -> data URL`, `attach_preview({path, imagesOnly?, root?}) -> preview`, `attach_reveal({path})`, `chat_interrupt({id})`, `chat_steer({id, text, now, attachments?}) -> string`, `chat_steer_cancel({id, noteId})`, `chat_set_model({id, model})`, `chat_set_permission_mode({id, mode})`, `chat_respond_permission({id, requestId, allow, always, remember?})` (`remember`: a remember option id; allows and applies it), `chat_respond_question({id, requestId, answers: string[][]})`, `chat_stop({id})`, `chat_replay({id}) -> {events, seq}`, `open_in_terminal({id}) -> number` (PTY id).

`chat_set_permission_mode` for Codex takes an approval policy (`untrusted`, `on-request`, `never`; codex-cli 0.145 refuses `on-failure` ("unknown variant"), so the composer no longer offers it and the core turns a saved `on-failure` into `on-request`) or a sandbox mode (`read-only`, `workspace-write`, `danger-full-access`); both apply from the next turn. `ready.permission_mode` reports the approval policy.

A prompt sent right after `start_chat` (before `ready`) is fine: Claude reads stdin in order after its `initialize`, Codex queues it until the thread exists. `user_message` may therefore precede `ready`.

Insights: `insights_status() -> {enabled, has_key, error}`, `insights_set_key({key})`, `insights_clear_key()`, `insights_set_enabled({enabled})` (persisted in the app's config dir, off by default). Sessions carry `insight: {headline, needs_you, generated_ms}` while insights are on.

`running_count()` and the quit confirmation (`confirm-quit`, payload: the count) include running chats; quitting stops chats and PTYs.

Events: `chat-event` `{ id: number, events: ChatEvent[] }` (batched, emitted when new events exist).

`sessions` payload gains `chats: [{id, provider, cwd, session_id, model, state, running, permission_mode, pid}]`.

Batches are pumped every ~16ms from a handle that never takes the Hub lock, so streamed text is live regardless of the 1s session refresh. The page applies them in one shared frame (`lib/frame.ts`, `chatQueue` in `lib/chat.ts`), about 30 a second, together with the reveal of the text being written and rising token counts: one store update and one render for everything that arrived since the last (while the window is hidden, a 120 ms timer stands in for frames). The pane around the timeline (header, composer, panels) reads the chat through `useChatShell`, which holds still while only the reply being written grows; the timeline reads the live chat. The UI replays every chat in `sessions.chats` once (`chat_replay`) and rebuilds it from the replay plus any live events with a higher `seq`, so a reload loses nothing.

## AI insights (optional, off by default)

Uses the Anthropic API with a key the person supplies (never bundled, never the CLI's login). Core module `crates/core/src/insights.rs`:

- Key lookup order: env `COOOL_ANTHROPIC_API_KEY`, then the macOS Keychain item with service `coool-anthropic-api-key` (account `coool`). Helpers to save and delete the Keychain item. Never log or serialize the key. Saving writes the command to `/usr/bin/security -i` on stdin, so the key never appears in a process's argv, and reads it back to confirm (the item stays one `security` owns, so reads never raise a Keychain prompt for the unsigned app).
- `Insight { headline: String, needs_you: Option<String>, title: Option<String>, generated_ms: u64 }`: `headline` is one plain line saying what the agent is doing or did (a status line: never the session's title, it changes every turn); `title` is the model's candidate title for the whole session (see "Session titles"; the same request, no extra call); `needs_you` is set only when the session is blocked on the person (a question, an approval, an error it cannot pass, a loop), saying what it needs.
- A scheduler that keeps cost negligible: only live sessions, only when their activity changed since the last insight, at most one request per session per 45s, a global hourly cap, small model (`claude-haiku-5-5`), short input (the current title, last prompt, a spread of up to 8 of the session's prompts, last ~40 activity lines, status, current tool), structured JSON output.
- The same switch, key and hourly cap also drive the AI read of permission requests ("What this does and why").
- App: Settings > AI insights (the full-screen Settings page) to paste a key (stored in the Keychain), an on/off toggle, and the insight shown on Mission control cards and sidebar rows; "Needs you" gets its own badge and sorts first.

## Session titles

A session's title follows what it is about instead of staying its first prompt forever. Core module `crates/core/src/titles.rs`; the app resolves every session's title on each refresh and sends it as `Session.name = { title, source, previous }` (`source`: `manual | cli | ai | auto | first`; `previous`: earlier titles, newest first, at most 5). The UI reads it only through `displayTitle` (`app/src/lib/format.ts`), so tabs, the sidebar, the chat header, Mission control, Needs you, the palette and chat notifications (`notify.rs` gets the same title) always agree.

**Where a title comes from**, highest first:

1. **A name the person gave in coool**: double-click the title in a sidebar row or the chat header (or right-click it: **Rename…**). Enter saves, Esc cancels, leaving the field saves, an empty name goes back to automatic. It is pinned: never replaced automatically, not even by a CLI rename. Right-click > **Use automatic title** unpins it. Stored in coool's data folder (`~/Library/Application Support/coool/titles.json`, `rename_session({ provider, id, name: string | null })`), never under `~/.claude` or `~/.codex`, so it survives restarts.
2. **A rename by the CLI itself**: Claude Code `/rename` (a `custom-title` record), or a CLI title that differs from its first value (Claude `ai-title` records; Codex thread names in `session_index.jsonl`, latest entry wins). Taken as soon as it appears.
3. **The automatic title.** It starts as the CLI's own first title (Claude's `ai-title`, Codex's thread name), else a short form of the *first* prompt (no longer the latest one, which changed every turn).

**The change rule (stability first).** The automatic title is re-evaluated only at a **checkpoint**: once the session has at least 4 prompts, every 12 prompts since the last checkpoint, and at every context compaction. At a checkpoint coool takes a candidate and replaces the title only when the candidate is **clearly about something else**: it shares fewer than half the content words (lowercased, plural-stripped, prefix-matched, stopwords dropped) of the shorter of the two. "Living chat titles" -> "Living titles and rename" keeps the old title; "Claude Code fast mode credits" -> "coool: desktop app built with Tauri 2" changes. Either way the next checkpoint counts from there, so a title changes at most once per 12 prompts or compaction, never on an ordinary turn. Prompt counts come from the whole transcript (a head-and-tail preview of a big file never makes a checkpoint). The previous title stays in `previous`.

**Candidates.**
- *Insights on*: the model's `title` from the session's latest insight (the insights request already sent per session; the prompt asks for a 2–6 word noun phrase naming what the whole session builds or fixes, no "Chat about…", and to return the current title unchanged unless the subject moved). With insights on, a due checkpoint waits for the model's title rather than flip-flopping through the fallback (an ended session, which gets no more insights, uses the fallback).
- *Insights off* (nothing leaves the Mac): first, after a new compaction, the CLI's own summary of the session (the compaction's "Primary Request and Intent", its first sentence without parentheticals, "X is a Y" as "X: Y"; rules and bookkeeping lines are skipped); else the headline of the recent prompt that best represents the last 30 substantial prompts (its first line that says *what*, skipping repo/rules boilerplate, list items, Codex's injected `AGENTS.md` / file context), chosen by how often its words recur across that window, later prompts winning ties. A headline only counts when it reads like a title (starts with a capital, not a question, not small talk like "also…" / "i think…", not a pasted command or image tag, not cut mid-sentence) and at least two of its words recur in a fifth of the window; otherwise the title stays.

**Search and tooltips.** The ⌘K palette and the pane picker also match previous titles (a little below a current-title match; the row then says "was: …"). A sidebar row's and the header's tooltip say "was: …" for the last two titles.

**Cost and privacy.** No extra model calls: the title rides in the insights request (`required: headline, needs_you, title`). Without insights nothing is sent anywhere. The cheap scan stays cheap: the parsers only count prompts and compactions and keep the first CLI title and `/rename`; derivation runs once per checkpoint.

The browser mock (`lib/mockTitles.ts`) shows the "Wire Tauri events…" session titled "Claude Code fast mode credits" for its first 9 seconds, then maturing to its real subject, and "RawLog offset fixes" as a name the person gave; renames persist across reloads.

## Plan usage

How much of the person's Claude subscription limits and Codex (ChatGPT plan) limits are used, and when they reset. Core module `crates/core/src/usage.rs` (`UsageMonitor`); check it against the CLIs with `cargo run -q -p coool-core --example usage_print` (`-- --files` for the free sources only).

coool never reads credentials (no `~/.claude/.credentials*`, Keychain, `~/.codex/auth.json`) and never calls an account API itself. Every number comes from a surface of the official CLI, which does the authenticated request.

### Payload

`sessions` gains `usage: { claude: PlanUsage | null, codex: PlanUsage | null }` (same event, same "emit only when changed" rule; usage changes rarely, so no separate event). `null` means nothing is known yet. Command: `usage_refresh({ provider: "claude" | "codex" })` asks for a probe now (past back-off and focus); the result arrives with a later `sessions` payload.

```ts
type PlanUsage = {
  provider: "claude" | "codex";
  plan: string | null;            // "Max 5x", "Pro", "Plus", ...
  windows: UsageWindow[];         // every limit the CLI reports, in its order
  credits: UsageCredits | null;   // Claude "extra usage" / Codex credits
  reset_credits: number | null;   // Codex: free full resets (weekly + 5 h) available
  reset_credits_expire_ms: number | null; // Codex: soonest expiry among the available reset credits (null: unknown / none expire)
  fetched_ms: number;             // when the newest number here was read
  source: "claude.get_usage" | "claude.cache" | "claude.stream" | "codex.app_server" | "codex.rollout";
  stale: boolean;                 // fetched_ms older than 15 min
  error: string | null;           // last refresh failed, or "plan limits don't apply" (API key etc.)
};
type UsageWindow = {
  id: string;            // Claude: "session" | "weekly_all" | "weekly_scoped:<Model>" | <kind>; Codex: "<limit_id>:primary" | ":secondary" | ":spend"
  label: string;         // "Current session", "Weekly (all models)", "Weekly (Fable)", "5-hour", "Weekly"
  kind: string;          // "session" | "weekly" | "spend" | the CLI's own group for unknown meters
  used_percent: number | null;   // 0-100; null once the window has reset since the reading
  resets_ms: number | null;
  window_minutes: number | null; // 300, 10080
  model: string | null;          // per-model weekly limit (Claude)
  severity: string | null;       // Claude, as the CLI says it: "normal" | "warning" | "critical" (seen), "limited" (a rejected stream event)
  binding: boolean | null;       // Claude: the limit currently in force (is_active)
  as_of_ms: number;              // windows can come from different sources
  detail: string | null;         // "Reset since the last reading", "rate limit reached", "20.00 of 50.00"
};
type UsageCredits = { enabled, unlimited, balance /* Codex, decimal string */, used, limit, used_percent, currency, detail };
```

### Reset credits (Codex)

Codex accounts can hold free "full reset" credits (`rateLimitResetCredits` in `account/rateLimits/read`: `availableCount`, plus `credits[]` with `status`, `expiresAt`, `title` such as "Full reset (Weekly + 5 hr)"). A credit is redeemed with the app-server request `account/rateLimitResetCredit/consume`, params `{ idempotencyKey: string, creditId?: string | null }` (no `creditId`: the backend picks the next available credit), answer `{ outcome: "reset" | "nothingToReset" | "noCredit" | "alreadyRedeemed" }`. Source: the installed CLI's own protocol, `codex app-server generate-ts` / `generate-json-schema` (0.145.0; in the stable, non-`--experimental` output: `v2/ConsumeAccountRateLimitResetCreditParams.ts`, `...Response.ts`, `...Outcome.ts`, `ClientRequest.ts`); the Codex TUI uses the same request.

- Command: `usage_reset_codex({ idempotencyKey }) -> "reset" | "nothing_to_reset" | "no_credit" | "already_redeemed"`, or an error string (the CLI's message, e.g. "chatgpt authentication required for rate limit reset credits", a timeout). Core: `UsageMonitor::redeem_codex_reset` runs a short-lived `codex app-server` in `$TMPDIR/coool-usage` with `initialize`, `initialized`, then the consume request (id 2), and then forces a Codex probe so the new numbers and the remaining count arrive with a later `sessions` payload.
- Spending a credit can't be undone, so the UI only calls it after an explicit confirmation. One idempotency key (a UUID) per attempt; "Try again" after an error reuses it, so a retry of a request that did go through answers `already_redeemed` instead of spending a second credit. `nothingToReset` and `noCredit` spend nothing.
- Never exercised against the real account by tests: the request lines and every answer are unit-tested (`usage.rs`), the UI against the mock (`?usage=limited`, `?usage=noresets`, `?usage=resetfail`).

Claude has no user-redeemable reset: Claude Code's rate-limit options are extra usage, upgrade and waiting (checked in 2.1.327), so its windows only reset on their own.

### Limits of what can be known

- Claude's plan limits are a 5-hour session window, a weekly all-models window and per-model weekly windows (currently one for Fable), plus optional extra-usage credits; Codex's (per `limit_id`, normally `codex`) are a 5-hour and a weekly window plus credits, an optional spend-control limit and redeemable reset credits. Both report percentages only, never absolute message or token budgets.
- Usage on other devices and on claude.ai / chatgpt.com counts against the same limits but only shows up after the next probe (or Codex turn on this machine). The free sources alone go stale while the person is not using the CLIs; the probe is what keeps an idle reading current, and it only runs while coool is in use.
- A window whose reset time has passed is shown with `used_percent: null` until the next reading (the new value is unknown, not zero).
- Undocumented surfaces: `get_usage` is marked experimental in the CLI ("the response shape may change"), `cachedUsageUtilization` is an internal cache, and the endpoint object carries many placeholder keys. The parser prefers `limits[]` and falls back to the named windows (`five_hour`, `seven_day`, `seven_day_opus`, `seven_day_sonnet`, `model_scoped`); unknown limit kinds are passed through with their own name. Claude `extra_usage` amounts are divided by `10^decimal_places` when that is given, which could not be checked on an account with extra usage on. Codex's app-server `account/*` methods are part of its generated schema (0.145) and the rollout `rate_limits` shape is the one the TUI writes; both are read case-insensitively (snake/camel).
- Verified with Claude Code 2.1.325 and codex-cli 0.145.0.
