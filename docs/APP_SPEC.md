# coool desktop app: spec v1

coool is an open-source workspace for agentic coding (coool.sh). People bring their own Claude Code or Codex subscription: coool drives the official `claude` and `codex` CLIs and never touches credentials. The Rust core (`crates/core`) already discovers sessions, parses transcripts and subagents, and runs CLIs in PTYs. The TUI (`crates/tui`) is one frontend. This spec is the second: a desktop app that should feel like a better Cursor / Warp / Codex app, built for running many agents across many projects at once.

## Stack

- **Tauri 2** (Rust backend in `app/src-tauri`, a workspace member depending on `coool-core`).
- **React 19 + TypeScript + Vite**, **Tailwind CSS 4**, **Motion** (`motion/react`) for animation, **xterm.js** (`@xterm/xterm` + fit + webgl addons) for terminals. pnpm.
- No component kit that needs a paid license. Build our own components.

## Product shape

Three regions, all resizable, all animated:

1. **Sidebar: projects.** Sessions grouped by project (the session's `cwd`; label = folder name). Each project row shows a live count and a combined status dot. Under it, its sessions: status dot (working = small blue spinner, waiting for you = solid green only until you open that chat (an unread mark: it returns when the chat finishes another turn), needs you = yellow with a slow pulse ring, ended = hollow grey), provider mark (claude / codex colour), title (the living title, CHAT_SPEC "Session titles": double-click or right-click to rename; the tooltip says what it was called before), one dim line with the current tool or "12m ago". Running subagents nest under their session. Ended sessions collapse behind a per-project "N earlier" disclosure. A "+" on each project starts a new session there; a global "New session" button sits at the top.
2. **Main: workspace.** Tabs across the top, one per open session, reorderable; a tab can be split right or down so two to four sessions are visible at once (this is the multitasking core; a simple recursive split layout is enough). With nothing open, the main area is **Mission control** (see "Mission control"): the agents' work across every project as live, glanceable views. Clicking a session opens it.
3. **Session view.** Two modes with an animated segmented switch:
   - **Activity** (default for sessions not run by coool): the transcript as a designed timeline. User prompts are prominent. Assistant prose is readable body text. Consecutive tool calls group into a collapsible **step list** ("Ran 6 steps") where steps appear one by one; the active step shimmers and shows a live timer. Subagent launches render as a nested card with the subagent's own live steps, its context fill and the lead's handoff (CHAT_SPEC "Sub-agent cards"). Errors are a quiet red row. Every tool call reads through one naming function (CHAT_SPEC "Tool rows"): MCP and device tools as phrases ("Opened affectui.com/components", chips "Browser ×13"), never as `mcp__server__tool`. A coool chat's finished turn shows where its time went under "Worked for …" (CHAT_SPEC "Where the turn went"). The live row of a running turn right-aligns "↓ 3.2k" (the turn's output tokens, dim, hidden at 0) just left of its timer; Jobs cards show their own output tokens the same way, subagent cards (Activity, Chat, Agents panel; running and finished) show Claude Code's own count, `tokens.total` = the agent's latest response's context (input + cache creation + cache read) plus its output (checked against Claude Code's recorded total: 249,702 computed vs 250,399 reported; the tooltip says what it is), and the finished-turn footer ("Worked for 5s") adds them. The turn number is `tokens.turn_output` on the wire (Claude: output tokens of assistant messages since the last prompt, once per message id; Codex: growth of `total_token_usage.output_tokens` since `task_started`), computed in `crates/core`, so it is right when coool opens mid-turn; coool's own chats use the chat's running output total minus its value at turn start, plus a live estimate while a response streams: the Claude chat backend counts streamed characters (text, thinking, tool-input JSON) at ~4 per token and emits `live_output` at most every 120 ms; the exact `usage` at `message_delta` replaces it, and the shown number (`outShown`) never steps back within a turn. Chat subagent cards use `agent_total` events (same formula).
   - **Terminal** (default for sessions run by coool): the real CLI in xterm.js, pixel-correct, themed to match.
   - A slim header: title (double-click or right-click to rename, CHAT_SPEC "Session titles"), project path, model, context meter (tokens.context against a 200k default scale), tokens in/out, and actions: Stop, Resume (ended sessions), Open in Terminal mode.
   - A **composer** docked at the bottom for sessions coool runs: multi-line, Enter sends, Shift+Enter newline. It writes to the PTY. For sessions running outside coool, the composer is replaced by a calm notice: "Running outside coool. Stop it and resume here to take control." with a Resume button once it is ended.

## Look and motion

Aim: calm, dense, precise; the motion is what makes it feel alive. Reference points the owner gave: inspora.design (curated modern product UI) and affectUI's "AI answer" and "thinking state" components (steps appearing one by one, live timer, streamed text, citation-style chips). Take the spirit, write our own code.

- **Type:** Geist (UI) and Geist Mono (code, terminal, numbers), bundled locally, not fetched at runtime. 13px base UI, tabular numbers for timers and token counts.
- **Colour tokens** (CSS variables, both themes; see `styles.css`). Neutrals: dark bg `#212121`, panel `#171717`, raised `#2f2f2f`, border `#383838`, text `#ececec`; light bg `#ffffff`, panel `#f9f9f9`, raised `#f4f4f4`, border `#e5e5e5`, text `#0d0d0d`. Error red `#ff5f57` (text `#d92d20` in light). **Status colours, one meaning each:** running / working (a busy session, a running subagent or shell, the active step, spinners, the Jobs button while jobs run, the step sweep) is Apple blue, `--status-running` `#0a84ff` dark / `#007aff` light (text the same); waiting for you / idle but alive is green `--status-waiting` `#28c840` (light text `#1a7f37`); needs you (permission prompts, questions, the pulsing ring, needs badges, the Needs-you view and its count) is yellow `--status-needs` `#febc2e` (light text `#9a6700`; a filled yellow badge uses dark ink `#2b1d00`); completed / positive is green `--status-done`, used only for small marks (finished subagent icons, done step-bar segments, success checkmarks, "Allowed", "Done"), never to flood a timeline; ended is grey, failed is red, stopped is faint grey. The TUI uses the same meanings (`crates/tui/src/theme.rs`).
- **Shape:** 10px radius on cards and inputs, 14px on sheets, hairline 1px borders, almost no shadows in dark, soft ones in light. Overlays (palette, sheets) use a light backdrop blur.
- **Motion rules:** springs for layout (tabs, splits, sidebar rows reordering as status changes: use layout animations so rows glide rather than jump), 150 to 220ms eases for hover and reveal, staggered entrance for step lists and Mission control cards, a shimmer sweep on "thinking" and on the active step, a soft pulse on working status dots, number tickers for token counts. New activity rows slide and fade in from below. Nothing blocks input; everything is interruptible. Looping activity animations (mood glyphs, the shimmering thinking word, thinking dots, running bars) are stepped, about 12 updates a second, and run only inside the session(s) open in the workspace panes: Home cards and sidebar rows show the same glyph and word static. **Reduce motion** (Settings > Appearance: Auto, On, Off; the row says which applies and why, and lists each Auto check with its reading) makes every loop static except a slow opacity breathe on the needs-you ring, and transitions instant or opacity-only. Auto reduces when macOS Reduce motion is on (`prefers-reduced-motion`), in Low Power Mode, when the thermal state is serious or critical, on battery below 20%, on weak hardware (an Intel Mac, 8 GB of memory or less, or 4 performance cores or fewer; read once), or when the Mac was busy at launch (whole-system CPU at 70% or more averaged over the first 20 s; decided once, kept for the session) (`motion_hints` / `motion-hints` from the backend).
- Empty and loading states are designed, not blank.

## Backend contract (Tauri)

State: one `Hub` behind a mutex, refreshed by a background thread whenever a file it reads changes (FSEvents / inotify on `~/.claude/projects`, `~/.claude/sessions`, `~/.codex/sessions`, `~/.codex/session_index.jsonl`, through `coool_core::watch`: the first change after a quiet spell refreshes at once, the rest of a burst at most every 30 ms), when coool itself starts or stops something, and at least once a second (200 ms while the initial load runs) for what no file write announces (a process that died, a session ageing out, plan usage, insights). Watching only: nothing there is written, and files coool never reads (`~/.claude/sessions/*.key`) are ignored.

Events (backend to frontend):

- `sessions`: the whole state, once, as soon as the app starts: `{ seq, order: string[], sessions: Session[], pending: number[], ...additive fields }` (`ptys`, `loading`, `chats`, `usage`, `show_automation`). `Session` is the serde form of `coool_core::model::Session` (see `crates/core/src/model.rs`; `updated` is epoch ms, `managed` is the PTY id or null), plus `insight` while insights are on. `order` is the key of each session in `sessions` (`provider:id`; a repeated id gets `#2`, `#3`), in display order.
- `sessions-delta`: after that, on every refresh that changed something: `{ seq, base, order, upsert: { [key]: Session }, patch: { [key]: SessionPatch }, pending, ...additive fields }`. It applies to the state numbered `base` (the previous payload's `seq`); `upsert` and `patch` hold only the sessions that changed, `order` lists every current key (a key not in it is gone), and the non-session fields are always complete. A frontend whose `seq` isn't `base` (it missed one, or just reloaded) calls `list_sessions` and continues from that. `app/src/lib/sessionsMerge.ts` rebuilds full snapshots from these (unchanged sessions keep their object), so the rest of the UI only ever sees `Snapshot`s; the browser mock hands over full snapshots directly.
  - A new session goes in `upsert`, whole. A changed session the frontend already holds goes in `patch`, unless the patch would be about as big as the session: a busy session changes several times a second, nearly always by a few timeline entries at the end, while its whole JSON (with every subagent's timeline) can pass a megabyte. `SessionPatch` is `{ head, activity, agents }`: `head` is every field except `activity` and `agents`, in full; the two lists are list patches `{ from, keep, edit: [[i, item]], tail: [items] }`, meaning "the held list's `keep` items starting at `from`, each `edit` replacing item `i` of those, then `tail`". In `agents`, `tail` items are whole agents and an `edit` item is `{ head, activity }` (the subagent's other fields, and its timeline as a list patch against the held one). A patch that doesn't fit what is held (`from + keep` past its end) is treated as a missed payload. Entries, subagents and lists a patch leaves alone keep their object identity, so memoised views (timeline blocks, agent cards) skip them. Built in `crates/core/src/wire.rs`, from one memo per session (the session as last sent and its JSON in parts): a session equal to what was sent is neither serialized nor sent, and a changed one serializes only its new or changed timeline entries.
- With `COOOL_TRACE_SESSIONS=<file>` set, payloads also carry `trace: { seq, at }` and the frontend reports when it applied each (`trace_sessions`); see `app/src-tauri/src/trace.rs`. Off otherwise.
- `pty-output`: `{ id: number, data: string /* base64 */, offset: number }` streamed from `Managed.raw` (poll `RawLog::read_since` every ~16ms per live PTY, emit only when there are new bytes).
- `pty-exit`: `{ id: number }`.

Commands (frontend to backend):

- `list_sessions() -> { seq, order, sessions, pending, ... }` (the state as last sent, same shape as the `sessions` event)
- `spawn_session({ provider, cwd, args?, rows, cols }) -> number` (PTY id)
- `resume_session({ provider, sessionId, cwd, rows, cols }) -> number` (claude: `--resume <id>`; codex: `resume <id>`)
- `pty_write({ id, data })`, `pty_resize({ id, rows, cols })`, `pty_replay({ id }) -> { data /* base64 */, offset }` (everything buffered so far, for a terminal that mounts late)
- `send_prompt({ id, text })` (uses `Managed::send_prompt`)
- `stop_session({ managed?: number, pid?: number })` (SIGTERM for external pids)
- `stop_shell({ pid })`: stops a background shell (see "Background shells"); refused unless a fresh scan still lists `pid` as a shell of a live session
- `shells_focus({ ids: string[] })`: the session ids on screen (every mounted session view); only their shells get output tails, and they are scanned every second
- `motion_hints() -> { low_power, thermal: "nominal"|"fair"|"serious"|"critical", on_battery?, battery_pct?, intel, memory_gb?, perf_cores?, busy_at_launch, reduce, reason? }`: device hints for "Reduce motion: Auto"; re-read every 15 s and pushed as `motion-hints` when they change
- `pick_folder() -> string | null` (dialog plugin)

Quitting the app stops the sessions it runs (confirm first if any are running).

## Who started it

Every `Session` carries `origin`: `user` (the person, in a terminal, IDE, desktop or phone client), `coool` (a chat or terminal coool started, remembered across restarts in `<data dir>/coool/own-sessions.json`), or `automation` (started programmatically by another tool or agent). Rules, from the CLIs' own records: Claude `entrypoint` `sdk-*`, `github-action`, `mcp` are automation unless a user turn was typed by a human (`turnOrigin` / `origin.kind` `human`); every other or unknown value is `user`. Codex `originator` `coool` is coool's, `codex_exec` and `source` `exec` / `mcp` are automation, subagent rollouts are attached to their parent thread as agents. Classified by how a session started, never by its folder.

Automation is hidden by default everywhere (sidebar, Home, palette, needs-you, counts); Settings → "Show runs started by other tools" lists it, dimmed with an `auto` tag, and the sidebar ends with "N runs by other tools hidden · Show". A hidden run that is live and needs the person is listed anyway.

Child runs: an automation session started from inside another session (found by walking its parent pids up to a registered session, or from the owner session id in an agent scratch path, and remembered) has `parent`; it is listed nested under that session (live ones always, two recent ended ones, then "Show N more jobs"), never as a row or card of its own, and its "Needs you" surfaces on the parent. A parent waiting for the person while children run (`live_children`) or while the CLI reports background tasks (`background_tasks`, registry status `shell`: a flag, no count; `shells` lists them, see "Background shells") is "Working in background": blue working spinner, "2 jobs running", a "Background" pill in its header. `waiting_for` (registry status `waiting`) means the CLI is blocked on the person.

## Background shells

`Session.shells: Shell[]` (left out of the JSON when empty; empty for ended sessions) lists the commands a live session runs in the background, from `coool_core::shells`, filled by `Hub::refresh`:

- **Found in the process tree**, no external commands: the children of the session's CLI pid (macOS `proc_listchildpids` / `proc_pidinfo` / `sysctl(KERN_PROCARGS2)`, Linux `/proc`), walked at most once a second for sessions on screen (`shells_focus`, every visible pane), with background tasks per their CLI, or with shells at the last walk, and at most every 10 s for the rest; between walks the last answer is reused. Each process is attributed to the nearest session above it (a nested `claude -p` child session keeps its own).
- **What counts.** Main signal: Claude Code's Bash wrapper, `zsh -c 'source …/shell-snapshots/snapshot-… && eval '<cmd>' < /dev/null && pwd -P >| /tmp/claude-…-cwd'`; the command shown is the `eval` word. Any other `<shell> -c <cmd>` child counts too (Codex runs its commands as `zsh -lc`; Codex sessions only have a pid when coool runs them). Never shells (`shells::HELPERS`): `caffeinate`, the `claude` / `codex` binaries, language servers (`*-language-server`, `rust-analyzer`, `gopls`, `pyright`, `sourcekit-lsp`, `clangd`, `jdtls`, `tsserver`, anything `--stdio`), MCP servers (anything whose command line says `mcp`, plus the programs in the project's `.mcp.json`). Other processes are walked into (two levels) but not listed. A command shows once it has run 3 s (quick foreground commands never flicker in), or at once when the transcript marks its call `run_in_background`.
- **`Shell`**: `pid` (the wrapper, which leads its own process group), `command`, `description?` (the Bash call's), `started` (epoch ms; the UI ticks elapsed time itself), `cpu` (integer %, the shell plus everything under it since the last walk; moves by 5 points or to/from 0, so deltas stay quiet), `output?` (the background output file the tool_result named), `tail?` (its last 3 lines, read from the last 4 KB, ANSI stripped, only for sessions in `shells_focus` and only when the file changed), `idle_loop` (a `sleep` + `until`/`while`/`for` loop at 0% for 45 s), `background`.
- **Matching to the transcript** (Claude): the parser keeps the last 32 background and 32 other Bash calls per transcript (session and subagents; cache v5). A process matches a call with the same command (whitespace collapsed, a leading `cd <dir> &&` ignored, as Claude Code drops it) made before it started (5 s skew), not already returned, closest in time, each call once. Unsure: the command alone.
- **Reads only**: no credentials (`~/.claude/.credentials*`, `*.key`, `~/.codex/auth.json`, Keychain), nothing written under `~/.claude` / `~/.codex`; the only files read are output files a transcript named as Bash background output, and only paths shaped `/tmp/claude-*/…/tasks/*.output` (or under `/private/tmp`), no `..`, never through a symlink.
- **Stop** (`stop_shell`): SIGTERM to the shell's process group when it leads one that isn't the session's, else to the pid; SIGKILL 3 s later if the same process (same start time) or group is still there.

UI: the Agents panel (it opens for shells alone too, and the first background shell opens it like a running agent) lists a small uppercase "SHELLS" label between running and finished agents, one compact card per shell: description (or the command in mono), the command dim and mono under it (or `pid · CPU` when there is no description), elapsed time ("2m 23s") right-aligned, a dim animated `run` glyph, a dim "idle loop" tag, the output tail folded by default, and Stop with a one-step confirm ("Stop?" for 3 s). A finished shell fades out; there is no history. The header Agents button shows only the number of running jobs (running agents + shells, "3 running"), or the agent count dim ("5 agents") when nothing runs; it appears when there are subagents or shells. "N jobs running" texts (sidebar tooltips, Home card line, the quiet live row) count child runs plus shells; "Background tasks" is left only for a registry `shell` flag with no listed shells. The browser mock has shells (`?agents=jobs`: agents and shells, `?agents=shells`: shells only).

Unread green dot: the store keeps `seen` (`coool.seen` in localStorage): a baseline set on first run (so chats already idle start as seen) plus session key -> its activity time (`last_event`, falling back to `updated`) when last looked at, entries older than 30 days dropped. A session on screen (active tab, window visible) is marked seen and re-marked when its activity time advances; opening a row marks it too. Unseen = waiting and activity time newer than seen. The activity time is `last_event`, the timestamp of the newest real conversation event in the transcript (a prompt, a reply, a turn end; Claude `user` / `assistant` / `system turn_duration` entries, Codex `response_item` and turn / message events), not `updated` (the transcript file mtime, which other tools also bump and metadata entries like queue-operation or api-request move): a file touched without new conversation does not bring the dot back. The core reads it from the file tail for chats not parsed yet and caches it. Older stored markers (mtime ms, never below the real event time) stay valid. Applies to sidebar rows, the collapsed summary count, Home cards, tabs and the palette; working, needs-you and ended are unchanged. The browser mock has no baseline, so its idle chats start unseen.

Sidebar cap: per project at most 5 rows at rest (every live chat, most urgent first, then the most recent ended ones); "Show N more" reveals 10 at a time, "Show less" returns to 5; the revealed amount lives for the app run only and resets when the project is collapsed or expanded. The open chat is always shown. Collapsed projects persist (localStorage) and show one dot per state inside (yellow needs you, blue working, green waiting, counting only chats you have not looked at yet; a count when more than one); clicking a yellow summary opens the chat that needs the person.

## Artifacts and the browser panel

Claude Code artifacts (pages a session published to claude.ai with its Artifact tool, parsed by `coool_core::artifact`) show as a card in the timeline: the newest version, earlier publishes folded into it. Nothing opens in another browser by default:

- **Preview** (hidden once the local copy is gone): the local copy in a **preview window** of its own, a small native window floating over coool like the browser's pop-ups (below).
- **Open** (globe icon): the claude.ai page, in a tab of the session's browser panel (the tab already on that URL if there is one). The person signs in to claude.ai once inside it.
- **Links in chat** (markdown links and bare URLs, which remark-gfm links) open in a tab of the same panel when they are http(s) (or focus the tab already on that URL); other schemes do nothing.

**The preview window** (`artifact_window({ url }) -> bool`, `app/src-tauri/src/artifact.rs`): a macOS window with a title bar, labelled `preview-<n>`, titled "<artifact title> · v<version>", 900×700 (smaller if the screen's work area is), centred on the main window and kept on its screen, resizable (at least 320×240), closable. It is a child window of the main window (`addChildWindow`: it stays above coool and moves with it, without blocking it), not a modal. One per artifact URL: Preview again focuses it (and reloads it when a newer version was published since). `false` (the card hides Preview; the start view opens the claude.ai page instead) when the local copy is gone. It closes with the main window. The browser mock opens the mock page in a pop-up window instead.

How it is built: the window loads a tiny host page as a `data:` URL (Tauri's `webview-data-url` feature): a meta CSP of `default-src 'none'; style-src 'unsafe-inline'; frame-src coool-artifact:` (no script, no fetch, frames only from the artifact scheme) and nothing but `<iframe sandbox="allow-scripts" allow="" referrerpolicy="no-referrer">` loading `coool-artifact://localhost/<token>/<published path>`. A token is minted only for an artifact the backend parsed itself and serves exactly its page and `files` map, never through symlinks. The window's navigations are limited to that host page (`data:`, `about:`) and that token on the artifact scheme; the web, `file:`, the app's own pages and other tokens are cancelled (a link to the web inside a preview does nothing: use Open). New windows are refused, downloads refused, and its data store is non-persistent.

Why not load the `coool-artifact://` page directly in the window: Tauri counts every registered custom scheme as a *local* origin, and the IPC lets a local origin call the app's own commands whatever its webview label (only plugin commands are checked against capabilities when the app has no command manifest). Tauri's script (with its invoke key) is injected into every main frame, so a top-level artifact page could call `list_sessions` and the rest. A `data:` document is a non-local origin, so every command and plugin call from it is checked against the ACL, which grants `preview-*` nothing; the artifact itself runs one frame down, sandboxed (opaque origin, no `allow-same-origin`, no popups, no top navigation), where Tauri injects no script and so it never learns the invoke key, exactly as the old in-panel preview did. The `browser` self-test runs the artifact probe inside the window (no `__TAURI_INTERNALS__`, parent blocked, opaque origin, supporting image loads, unmapped files and `../` 404, raw `ipc://` fetch refused) and the browser's IPC probe in the window's own top frame, where Tauri's script and invoke key are (`selftest_log`, `list_sessions`, `plugin:window|is_maximized`, `plugin:event|listen`: none answers; the calls never even reach Tauri, since wry builds each IPC request from the sending frame's URL and drops one whose `data:` URL isn't a valid request URI; were it delivered, it would be a remote origin with no capability). The raw `ipc://` fetch is blocked by the host page's CSP.

**Tabs.** Per session the browser panel holds tabs (`store.browser[key] = { tabs, active }`; each tab: its page, where it last was and its title). A compact strip at the top of the panel: a globe, the title (or the host, or "New tab"), a close × on hover (a middle click closes too), and "+" for a new tab with the start view. Clicking a tab switches; only the showing tab's webview is shown, the others are hidden. No Cmd+T / Cmd+W: those are the app's New session and Close tab. Under the strip: back, forward, reload (a spinner while loading), the **address field**, **Open in default browser**, and close (the whole panel). The address field shows where the page is; clicking it makes it editable (the full URL, selected): Enter goes there in this tab, Escape puts the old address back. It takes http(s) URLs and bare domains or `host[:port][/path]` (https:// is added; a bare word without a dot, other than `localhost`, is refused, as is every other scheme, with a red tint).

Closing a tab destroys its webview (and its pop-ups); the tab to its right shows, else the one to its left. Closing the last tab, or the panel's close, closes the panel, destroys every tab's webview, and remembers the tabs (where each page had got to, its title, the active one; this run only, `store.lastBrowser`). Hiding the panel (Escape, switching to Jobs / Models, another pane tab) only hides the webviews, history kept.

**The header's globe** is always in the session header. It hides the browser when it shows; otherwise it shows the hidden tabs, or restores the remembered ones (only the active one gets a webview right away; the others load where they were when shown), or, if the session never had a page, opens a tab with the **start view**: an address field (focused; same rules as the address field) and "From this chat": the chat's artifacts (newest publish of each; opens the preview window, or the claude.ai page in this tab if the local copy is gone) and the http(s) links in its prompts and replies, newest first, each once, at most 12. Its tooltip names the active page and how many more tabs there are. When the pane is too narrow for the browser, clicking it only shows a toast.

**The in-app browser** (`app/src-tauri/src/browser.rs`, `app/src/lib/browser.ts`, `components/BrowserPanel.tsx`) shows each tab in a native child webview of the main window (Tauri's `unstable` feature, `Window::add_child`), label `browser-<n>`, created when the tab first shows. Memory stays bounded: at most 4 webviews are alive across all sessions; beyond that the least recently shown one is destroyed (with its pop-ups, `browser-closed` to the app), and its tab keeps the URL it had got to and loads it in a new webview when it shows again (the page reloads; its back/forward history is lost). Not an iframe: claude.ai and most sites refuse to be framed, and claude.ai needs the person's login. It is laid exactly over the panel's body: the frontend measures that element (ResizeObserver on it, its panel and the pane, window resizes and visibility, the panel's kind attribute, then animation frames for 600 ms while springs settle) and sends `browser_bounds({ id, bounds: { x, y, w, h, visible } })` in CSS pixels, serialized so calls land in order. It is visible only while the panel shows it fully open (hidden while the panel slides or cross-fades), while no sheet or palette is open and no popover overlaps it (popovers register in `lib/overlays.ts`), and while the window is visible; the app's webview takes the keyboard back whenever it hides. Toasts move left of it. It leaves the panel's 5px resize edge uncovered. Title, URL, loading and history state come back as `browser-state` events (page loads, title changes, and a 1.5 s poll while shown for in-page navigations), sent to the `main` webview only.

Commands: `browser_open({ url, bounds }) -> id`, `browser_bounds`, `browser_navigate({ id, url })`, `browser_go({ id, action: back|forward|reload|stop })` (macOS: WKWebView's own history), `browser_poll`, `browser_close`, `browser_open_external({ id })`. Events: `browser-closed` (id) when the backend closed one; `browser-new-tab` (`{ id, url }`) when a page asks for a tab. The browser mock (`pnpm dev`) frames web pages in a sandboxed iframe instead.

**Its own profile.** Cookies and site data live in a WebKit data store of their own (macOS 14+: `data_store_identifier`, fixed so logins persist; older macOS falls back to the default store; Linux / Windows: `<app local data>/browser`), never read or logged by coool. The self-test uses a non-persistent store. The user agent is desktop Safari's (WebKit's default lacks `Version/… Safari/…`, which some sign-in pages refuse). Downloads are refused.

**Pop-ups and new tabs.** The webview's new-window handler (`WebviewBuilder::on_new_window`) decides from the window features WebKit passes (`browser.rs` `new_window_kind`):

- `window.open` **with** a size (`width` and `height`) or a position (`left` and `top`): a pop-up window (below), so `window.opener` works.
- A link with `target=_blank`, or `window.open(url)` **without** features (WebKit passes no size and no position): a **new tab** in the panel, right after the page's own tab, and it shows. The page gets no window back (`window.open` returns null, no `opener`). A pop-up's own unsized requests open tabs in the panel its chain started from.
- A page that is not http(s) yet (`window.open()` / `about:blank`, then scripted by its opener): a pop-up window.
- Anything the browser may not show (other schemes, the app's origin): refused.

For `target=_blank` links to reach the handler at all, the opener plugin's click-to-open script is off (`open_js_links_on_click(false)`): Tauri injects plugin scripts into every webview, and that one turned each `target=_blank` click in a browser page into a `plugin:opener|open_url` call, which the browser webview may not make, so the click did nothing. The app's own links open through their handlers (`Markdown.tsx` prevents the default and opens a tab).

WebKit reports a size only when both `width` and `height` are given (and a position only with both `left` and `top`), so `window.open(url, "", "width=500")` alone opens a tab.

**Pop-up windows** open as real windows, as in Safari, so sign-ins that talk back to their opener work (claude.ai's "Continue with Google": Google Identity Services opens `accounts.google.com` in a pop-up and posts the result to `window.opener`). For them the handler (Tauri 2.12 `unstable`) returns `NewWindowResponse::Create` with a `WebviewWindow` labelled `popup-<n>` whose WKWebView is built from the `WKWebViewConfiguration` WebKit hands to `createWebViewWithConfiguration` (`window_features`): that is what keeps `window.opener`, and it carries the opener's data store, so cookies land where the panel needs them. The window is the page's `width`/`height` or 500×650, centred on the main window, resizable, titled with the page title; desktop Safari user agent; downloads refused; its navigations follow the panel's rules (http(s), `about:`/`blob:`/`data:`; nothing else, not the app's origin), and a pop-up's own pop-ups are pop-ups too. A page's `window.close()` closes it: wry's UI delegate lacks `webViewDidClose:`, so `browser.rs` adds that method to wry's delegate class at runtime, and it only ever acts on a tracked pop-up's webview. Pop-ups close when their opener webview is destroyed (the panel's close, the 4-alive eviction, their opener pop-up closing) and when the main window goes; a pop-up that ends on an ordinary page stays a small window until closed. The app's close-confirmation (`CloseRequested` while sessions run) applies to the main window only. What the person sees for Google: clicking "Continue with Google" on claude.ai opens a small "Sign in – Google Accounts" window over coool; after choosing the account it closes by itself and the panel's claude.ai page finishes signing in.

**Security.**

- The child webviews have no access to coool's IPC. The capability (`capabilities/default.json`) is scoped by **webview** label `main`, not window: a window-scoped capability also covers every child webview of that window. It has no `remote` section, and Tauri checks every command and plugin call from a non-local origin against the ACL, so remote pages are refused everything, app commands included. Verified by the `browser` self-test: a probe page served from 127.0.0.1 (a remote origin) calls `selftest_log`, `list_sessions`, `plugin:window|is_maximized`, `plugin:event|listen` and a raw `ipc://` fetch; all are refused.
- Pop-up windows (`popup-<n>`) are in no capability either (the only capability names the webview `main`), and their pages are remote origins. They share the opener's user content controller (wry skips its own IPC handler for a webview built on an opener's configuration), so anything they post arrives as the opener `browser-<n>`, which has nothing. The self-test runs the same IPC probe from inside a pop-up: all refused. It also checks that the pop-up has `window.opener`, posts back to the opener (which shows it in its title, read through the panel's title polling, no IPC), closes itself with `window.close()`, uses the Safari user agent, and that a pop-up left open closes with the panel. The same scenario checks the tab side: a `target=_blank` link (clicked for real: `selftest_click` sends an AppKit mouse down and up to the window, so the click is trusted and a fresh user activation; nothing is posted to the system and the pointer doesn't move) and a bare `window.open` each open a tab (no window), switching tabs swaps which webview shows, closing a tab destroys its webview, Open adds or focuses a tab, an evicted tab reloads where it was, and closing / restoring keeps the tabs.
- Only http(s) pages: the commands accept nothing else (no credentials in the URL, not the app's own dev-server origin, not a `*.localhost` custom-protocol host), and a page's own navigations to any other scheme (`file:`, `javascript:`, `tauri:`, `ipc:`, `coool-artifact:`, app links) or to the app's origin are cancelled; `about:`, `blob:` and `data:` frames are allowed (no local privilege). The `coool-artifact://` frame in the preview window stays the only custom-scheme page coool shows, sandboxed without `allow-same-origin`. (Custom schemes are registered on every webview, so a remote page could request a `coool-artifact://` URL, but only with a preview token, which it never sees.)
- Preview windows (`preview-<n>`): see "The preview window" above.
- The opener plugin's JS scope stays `https://claude.ai/*` (outside a session view, Open sends the claude.ai page to the default browser). For a web page, "Open in default browser" is `browser_open_external(id)`: Rust reads the URL that webview shows, re-validates it as http(s) and opens it with the opener from Rust, so the main webview never gets a general open-any-URL permission.
- coool never reads the CLIs' credentials (`~/.claude`, `~/.codex`, Keychain); the claude.ai login is the person's own, typed into the webview.

Known limits: while the page has keyboard focus, the app's web shortcuts (Cmd+K and friends) go to the page; native menu shortcuts still work. Email links open in the person's mail app and default browser, not here.

## iPhone panel (iOS Simulator) and the `coool-device` MCP server

The idea: agents (and the person) test and drive apps inside coool's right panel, on a device of their own, instead of opening windows that take over the screen while the person works on something else. Phase 1 is the iOS Simulator; phase 2 is a sandboxed Mac (a Virtualization.framework VM) behind the same header button and the same MCP server.

**The header.** Three icon buttons sit where the globe was, left to right: **Browser** (the globe, spinning while a page loads), **iPhone**, **Mac** (the sandbox Mac, see "Mac panel (sandbox VM)"), then Jobs. Each toggles its environment in the right panel: one at a time; clicking the active one closes the panel, clicking another switches. Selected = background only, the icon keeps its colour. Each chat remembers which was open (`rightPanel[key]`), so closing and reopening restores it. While the chat's agent drives its iPhone and another panel is showing, the iPhone button shows a small breathing blue dot (4 s after the latest action).

**The panel** (`components/DevicePanel.tsx`, panel kind `device`, store `device[key] = { udid }`): 340–720px wide (default 400, resizable by its left edge, `coool.deviceWidth`), shown in panes at least 660px wide (else a toast). Top bar: the device picker (state dot, name, state; coool's own devices first, then the person's under "Your simulators"), Boot / Shut down, Home (also ⇧⌘H), Lock, close. No device yet: the first coool device; none exists: "Set up iPhone" creates **coool iPhone** (newest iOS runtime, newest non-Max iPhone Pro) and boots it. No Xcode: a calm empty state with the reason. Not booted: a black screen in the device's shape with Boot; Booting… / Shutting down… with a spinner; errors inline with "Try again". The live screen keeps the device's aspect (18px padding, corners 6% of its width, hairline ring) and streams only while the panel shows a booted device (detached when hidden, switched, unmounted). Input: pointer down / move / up become touches in device points (moves throttled to one per frame, pointer captured); click focuses the screen (soft ring); printable keys are typed, Enter / Backspace / Tab / Escape / arrows are keys (Escape on a focused screen doesn't close the panel), Cmd+V pastes the clipboard's text, other Cmd/Ctrl shortcuts stay the app's. Agent activity is shown as agent presence (see "Agent presence" below): the acting agent's cursor and label over the screen, and the beam around it. Agent activity in a chat sets that chat's device and opens the iPhone panel when no panel is showing (not again for 30 s if the person closed it during that stretch). Picking a device calls `sim_bind(chat, udid)`, so the agent acts on what the person sees. The browser mock has two devices, a generated home screen and a fake agent tap every 6 s.

**Never steals focus.** `simctl boot` is headless; Simulator.app is never opened; nothing activates a window. coool only creates, erases or deletes devices of its own (named "coool …"); the person's simulators can be booted / shut down from the panel and selected, nothing more. Devices coool booted are shut down when coool quits.

### Backend (`app/src-tauri/src/device/`)

- `simctl.rs`: lifecycle through `xcrun simctl` (list, create coool's device, boot + bootstatus, shutdown, install, launch, terminate, openurl, ui appearance, location, privacy, pbcopy, listapps).
- `helper.rs` + `native/coool-sim.m`: **coool-sim**, our own Objective-C helper (no idb, nothing downloaded). build.rs compiles it with `xcrun clang`; the app embeds the binary and writes it to `<app local data>/bin/coool-sim-<hash>` on first use. One process per booted device, stdin JSON lines in, framed stdout out (`[u32 len][u8 kind]`, `J` JSON / `F` JPEG). It loads CoreSimulator / SimulatorKit / AccessibilityPlatformTranslation at runtime (nothing links privately) and:
  - **frames**: registers SimScreen frame callbacks on the device's display IO ports and takes the surface whose size is the main screen; each presented frame is scaled and JPEG-encoded with CoreImage, coalesced to ≤30 fps, only while someone watches. (Never call the display descriptor's synchronous getters on Xcode 27: they block. Setup runs off the main thread: the remote proxies answer on the main queue.)
  - **input**: Xcode 27 (CoreSimulator ≥1155.4) drops the legacy Indigo HID path, so input goes to the guest's `dtuhidd` (`com.apple.coredevice.feature.remote.hid.digitizer`) over XPC: the service's port from `-[SimDevice lookup:error:]`, wrapped with `xpc_endpoint_create_mach_port_4sim` + `xpc_connection_enable_sim2host_4sim`, a liveness barrier, then `IndigoDigitizerEvent` (normalized touch), `IndigoButtonEvent` (home 0x0C/0x40, lock 0x0C/0x30, …) and `IndigoKeyboardButtonEvent` (US-layout HID usages; non-ASCII text is pasted via `simctl pbcopy` + Cmd+V).
  - **UI tree**: `AXPTranslatorRequest`s sent with `-[SimDevice sendAccessibilityRequestAsync:…]` (frontmost application, then one multiple-attribute request per element: frame, role, label, value, identifier, enabled, selected, focused, placeholder, children) — the assistive-technology view, typically 10–50 elements.
  - **idle**: "no frame presented for N ms", the settle signal.
- Technique learned from facebook/idb (MIT; FBSimulatorControl HID/XPC/Framebuffer, FBSimulatorAX), reimplemented.

**Spike (Apple silicon, macOS 27.0.1, Xcode 27, iOS 27.0, iPhone 18 Pro):** `simctl io screenshot` 420–1840 ms per frame (unusable for live view). coool-sim: JPEG frame (900px) 2 ms to encode (11 ms first), ~57 KB, 0 fps on a still screen, ~21 fps while animating; accessibility read 15–80 ms (14–45 elements); tap 62 ms (40 ms of it the touch's hold); typing "Hello, World! 123" 37 ms, correct; home button 85 ms. idb_companion was not used: it drives the same private APIs plus a gRPC server and a Python client (more hops), only its newest builds speak DTUHID, and it would be a downloaded binary.

Commands: `sim_devices() -> { available, reason?, devices: [{ udid, name, state, runtime, deviceType, coool }] }`, `sim_ensure_device() -> udid`, `sim_boot({ udid })` (resolves when booted), `sim_shutdown({ udid })`, `sim_attach({ udid, frames: Channel }) -> { w, h, scale, stream }` (raw JPEG bytes on the channel), `sim_detach({ udid, stream })`, `sim_input({ udid, input })` (`touch` down/move/up x,y · `button` · `key` name + modifiers · `text`), `sim_bind({ chat, udid })`. Events (to `main`): `sim-state` (`{ udid, state }` on Booting / Booted / Shutting Down / Shutdown), `sim-activity` (`{ udid, chat, source: agent|user, kind: tap|swipe|type|press|app|observe|device|end, x?, y?, x2?, y2?, label? }`, points).

### The `coool-device` MCP server (`device/mcp.rs`)

Every chat coool starts gets it automatically, bound to that chat's panel device (else coool's own device, created and booted on first use; the panel follows). Claude Code: `--mcp-config=<json>` and `--allowedTools=mcp__coool-device`; Codex: `-c mcp_servers.coool-device.command=… .args=[…] .env={…}`, `.default_tools_approval_mode="approve"` (Codex's own prompt for MCP tools is an elicitation coool can't answer) and `.tool_timeout_sec=900` (Codex's 60 s default would cut a call that waits for the person or runs a pilot goal). That pre-approval only makes the tools callable: whether a call may go ahead is decided by coool's own permission gate inside the server (see "Device permissions"), the same way for both CLIs. Nothing is written to the person's CLI config (`coool_core::chat::McpServer`, `Hub::set_chat_mcp`).

Transport: the server's command is coool's own executable with `--coool-device-mcp` (`main.rs` checks it before starting any UI): a tiny proxy that connects to the app's Unix socket (`<app local data>/device-<pid>.sock`, falling back to the per-user temp folder when that path is too long for a socket; mode 0600; stale sockets of dead coool processes are removed), sends the chat's token (random per chat, per launch, via env `COOOL_DEVICE_TOKEN`) and pipes newline-delimited JSON-RPC both ways. Unknown tokens are refused. No network port, nothing else exposed. `coool --coool-device-serve <dir>` runs the server without the UI (prints `{ socket, token }` for chat 0) for scripted tests.

Tools (MCP 2025-06-18; every action returns the screen after it settles — the change has started (up to 400 ms) and at most 2 frames came in the last 150 ms — or "Screen unchanged (N elements).", plus `(act · settle · observe)` timings; `observe: false` skips it):

| tool | arguments |
|---|---|
| `observe` | `screenshot?` (adds a JPEG, longest side `max_size` default 800), — returns the listing below |
| `tap` | `target` (element id) or `x`,`y`; `hold_ms` (≥500 long-press) |
| `type` | `text`; `into` (tap this id first), `clear` (Cmd+A, Backspace), `submit` (Return) |
| `swipe` | `scroll`: up/down/left/right (`in` a scroll view id, `amount`), or `from`/`to` (id or [x,y]), `duration_ms` |

### Agent browser tools (`browser_*`, `device/web.rs`, `device/web_agent.js`)

The same `coool-device` server (one per chat, one tool family) also drives that chat's **Browser panel**, so an agent tests a web app in the panel beside the chat instead of opening Chrome or taking over the screen. The tools never open the system browser and never activate a window.

- **Which page.** The frontend reports every chat's browser tabs to the backend on each change (`browser_agent_sync({ chat, tabs: [{ tab, kind: web|start, id, url, title }], active })`, from `lib/browserAgent.ts`); a tool acts on the chat's **active tab**, the one the person sees. Only `browser-*` webviews are accepted (never `main`), and a chat's token only reaches its own chat's tabs. Opening and changing tabs go back to the frontend, which owns the tab strip: `browser-agent` events `{ chat, op: open|new|switch|close|ensure, url?, tab? }`; the tool waits for the sync that follows. `open` (browser_navigate when the panel has no page, or only a new tab) works like a link from the chat: the page opens in the panel and the panel shows. When the chat's view isn't on screen (another pane tab in front, a pane too narrow) the page opens **hidden** at the panel's usual size and the tools still work (`ensureNative` in `lib/browser.ts`); the panel moves it into place when it shows. `ensure` brings back a tab whose webview the app closed (more than 4 alive).
- **How.** One page script (`web_agent.js`) run with `evaluateJavaScript:inFrame:inContentWorld:completionHandler:` in a WKContentWorld of coool's own (`coool-agent`), so the page can't see its globals or patch what it uses; it returns JSON. No tool runs the agent's own JavaScript. It reads the DOM only: never cookies, localStorage, sessionStorage or IndexedDB (a unit test checks the script never names them). **Password fields** (and `autocomplete` current/new-password, one-time-code, cc-number, cc-csc) are masked: observe says only `(filled, hidden)` / `(empty)`, typing into one reports the character count, the activity label is `••••`; Rust's renderer drops a masked field's value even if one were sent.
- **Settling.** No fixed sleeps: the page script's `idle` op answers, polled every ~20 ms, by one of three rules. A MutationObserver in coool's world (ignoring coool's own cursor and highlight) notes each change against the node it happened on (a sample per node per 50 ms, kept 3 s).
  - **Continuous change** is told apart from change an action caused: a node changed 6+ times over 500+ ms of the last 1.2 s (a 100 ms timer, a JS-driven animation), or 2+ times over 400+ ms in the 2 s before the action began (a clock, a carousel), is *changing on its own*. CSS animations make no DOM changes at all.
  - **After an action** (click, type, select, press, scroll, a batch step, a pilot step): not loading, no click still on its way, and no change for 90 ms other than at the nodes changing on their own, counted from when the action began (so at least 90 ms). At most 1.5 s. When nodes keep changing on their own the result says so: `(act 2 ms · settle 92 ms · the page keeps changing on its own (3 spots: a timer, an animation or a carousel); not waited for)`.
  - **After a navigation** (navigate, back, forward, reload, a new tab): first, until the old document is replaced (a new document token, or for a same-document navigation a new URL; at most 3 s); then loaded (`loadEventEnd`), fonts loaded, quiet as above for 90 ms, or for 300 ms while the page's scripts are still drawing it (it changed after load, within 3 s of load); and, on such a page (or one with no text yet), something drawn in the middle of the viewport (25 points over its central half hit text, an image, media or a control), waited for at most 2 s after load. A page with scripts that changed nothing yet gets 300 ms after load to start when its middle is empty; a page without scripts, or a short one whose middle is empty, is done at once. At most 10 s. The result says when the middle still showed nothing, or when it gave up while the page was still loading or changing.
  - **`browser_wait_for` idle** keeps the strict rule: no change at all for 90 ms; a page that never stops changing times out and says so.
  - Measured (self-test `browser-settle`, a local site, Apple silicon): a client-rendered page drawing its content 300 / 550 / 800 ms after load returned its content 0 / 6 times before, 6 / 6 after (navigate 0.65 / 0.9 / 1.17 s; before 0.14 s with an empty frame); a plain static page 20 ms (before 106–190 ms); a click on a page with a 100 ms timer, a JS progress bar and a carousel 90–210 ms (before 1.5 s every time; 0.58 s right after load, before the page's own churn is known), and navigating to it 20 ms (before 10 s, the cap). Two more found by the sweep (a page whose body holds an inline script, its content small and centred): the script's own source counted as the page's text, so navigate returned after the 300 ms grace with the content still missing (4 / 6 empty); and the 25-point middle check missed a short centred message, waiting the full 2 s. Now only text outside scripts and styles counts, and any laid-out text in the central half counts as drawn: 6 / 6 with content at 0.61 / 0.87 / 1.12 s.
- **Ids.** Numbers, per document: an element keeps its id while it stays on the page (a WeakMap), new elements get new numbers, numbers are never reused within a document. Each observe carries a document token; an id sent after the page navigated or reloaded is refused ("observe again"), so an old id can't hit an element of the next page.
- **Navigation rules.** `browser_navigate` / `tabs new` take what the panel takes (`browser::loadable`: http(s) only, no credentials, not the app's own dev server or `*.localhost`); a bare host gets `https://` (`http://` for localhost and IPs). Pages' own navigations keep browser.rs's rules.

### Device pilot (`pilot_run`, `device/pilot/`)

A big model driving a device one `observe` / `tap` call at a time pays a model round trip per step. The **device pilot** is a System-1 loop in the Rust core, next to the device server, that takes a whole routine goal from the chat's agent and drives the chat's **iPhone or Browser panel** to it, then returns. Design input: `spikes/pilot/RESULTS.md` (Claude Haiku picks the right action 83% of the time, local MLX models at most 56% with no usable confidence, so there is no local model for now; muscle memory recognised 69% of screens on a repeat run in under 1 ms; Haiku's weakest decision is judging when it is done).

**The tool.** `pilot_run({ goal, target: "iphone"|"browser", app?, url?, inputs?: {name: value}, success?: [check], max_steps? (15), budget_ms? (90000), answer_alerts? })`, listed first in `coool-device`; its description and the server's instructions tell the calling agent to delegate routine multi-step navigation and form filling to it and to always give checkable success conditions. Checks: `{text_visible}`, `{text_gone}`, `{element: {label, value?}}` (a value may sit in the label: iOS reads "iOS Version, 27.0"), `{url_matches}` (substring). The answer is one summary line, then JSON: `status` `done` | `stuck` | `surprised` | `out_of_budget`, `verified` (every check holds on the final screen), `reason`, the `steps` (action, decider, perceive / decide / act / settle ms, note), `deciders` (steps per decider), `wall_ms`, `start_ms`, Haiku's cost and tokens (and how many were cached), the checks and the final screen. `stuck` and `surprised` also carry the candidate actions with each target's element id, so the caller can take over with `tap` / `browser_click`.

**The loop** (`pilot/mod.rs`, `run`): start (iPhone: a warm start when it can, below, else `app` is launched fresh with `simctl launch --terminate-running-process` and the pilot polls until the app is in front with its first screen built, two reads alike; browser: `url` is opened in the panel), then per step: perceive → check (all success checks hold: `done`, verified) → build typed candidates → decide → act → settle.

- **Warm start** (iPhone, a goal with `app` and checks that has a learned **route**): a relaunch costs ~3.5–4 s (SpringBoard answers for ~2 s of launch animation, then the app's first full tree read takes 1–1.5 s), so when the app is already running the pilot uses it as it is. The route (`memory::Route`, kept per goal next to the muscle memory) is the screen signatures and action keys of the goal's last verified run, from the app's first screen to the end. The app in front (or brought to the front with a plain `simctl launch`, no terminate, then the switch animation waited out) is recognised by `warm_plan`: on a route screen, by exact signature and only when the route shows it once and no earlier step typed text (a field's contents aren't in the signature), the run continues there with that step's previous action, so muscle memory replays exactly as in a learned run; on the route's end (its signature, or the goal's checks holding, since an end screen often shows live values like "Available, 48.87 GB") and reached by a tap, it goes back one screen, which must then be exactly the route's screen before; anything else (another app or screen, an alert, an ambiguous or typed-past screen, a back that lands elsewhere) relaunches. A warm run that succeeds splices its path onto the route's first screens. The start note says which (`warm: Settings was in front (50 ms), on the learned route's last screen; went back to screen 2 of 3 (1529 ms)`).

- **Candidates** (`candidates`): `{id, verb: tap|set_text|submit|scroll|back|launch|press|done|stuck, target: {role, label, value, frame, id}, input_key?, app?, key?}`, numbered. Taps on what can be tapped (buttons, links, cells, full-width text rows), `set_text <key>` per text field and input name, `submit` while a field has focus, scroll down / up, back, done, stuck; at most 40 element actions. Elements outside the screen (including the previous screen of a navigation push, which stays in the tree shifted left) and disabled ones aren't offered. On a system alert only its buttons are offered. The Mac also gets `launch app "<name>"` first (open it, or bring it to the front, through `mac_app`; the installed apps the goal names as words, read once per run from the guest's application folders, else every installed app up to 60) and `press command+n` (new window / document) and `press escape` (close a menu, dialog or panel); its taps, menus and scrolls alone couldn't open an app (it went in circles in Finder). **The pilot never invents text**: `set_text` types `inputs[key]` and replaces the field's contents (iPhone: tap, Cmd+A, Backspace when it held something, then type; browser: `browser_type`, which replaces).
- **The cascade.** (1) **Muscle memory** (`pilot/memory.rs`): the key is (goal words + target + app/url + input names, the exact screen signature, the previous action); the value an action key (verb, role, label, input, direction — no coordinates). Learned only from runs that end `done` (verified when checks were given), and only from steps that changed the screen; replayed only on an exact match and never twice on a screen that didn't change. One JSON file per project (hash of the chat's folder) under `<app local data>/pilot/` (the self-test's own folder in a test run), nothing in the project. (2) **Claude Haiku** (`pilot/haiku.rs`, `claude-haiku-5-5`), through the Anthropic key coool already keeps for insights (Keychain service `coool-anthropic-api-key`, account `coool`; never logged, scrubbed from errors): one forced tool call `act({action_id})`, no thinking, low effort, 8 s timeout. The tools and system prompt never change, so they are one cached prefix (`cache_control` on the system prompt); the step (goal, input *names* — values never leave the machine —, the checks, steps so far, visible text and the numbered actions) is the only new part. (3) Otherwise the run returns `stuck` (no key: "no remembered step for this screen and no Anthropic API key…", with the candidates) or `surprised`.
- **Done is judged by the checks**, not the model: when checks were given, "done" while they fail is rejected (twice: `stuck`). Without checks the model's "done" is accepted and reported unverified.
- **Signature** (`signature`): app, alert, keyboard, and each visible element's kind, role, label, state (values of toggles and other elements; text fields only filled / empty, since typed values vary) plus the page's visible text; positions are left out. On the iPhone, what comes and goes on one screen is left out too (`transient`): a row cut by the screen's edge, an empty unfocused search field with its Dictate button (iOS 27 Settings' floating search bar lingers on General after the push), and the navigation bar's back button (it joins the tree a moment after a push looks settled). Before this a pushed General screen had four signatures depending on timing, so memory missed on it about half the time and a warm start couldn't recognise it.
- **Stable reads** (iPhone `perceive`): a screen counts once a second read 80 ms later agrees (up to 1.2 s); the tree lags the frames, so a single read right after a settle could still be mid-transition. Costs ~80–140 ms per read.
- **Text field contents are never shown**: candidates give a filled field's value as `<filled>` (before, a filled field's text went to the model and into a stuck run's candidates).
- **Surprised**: a system alert the pilot hasn't learned (unless `answer_alerts`), the home screen after the app was up, or another app in front. **Stuck**: the decider says so, its call fails, an action fails, or the same screen comes back a fifth time. **Out of budget**: `max_steps` or `budget_ms`.
- **iPhone driver** (`pilot/drivers.rs`): the tree is read with the helper's `describe` (`visibleOnly`: off-screen subtrees aren't walked); SpringBoard in front with no name is a **system alert** (texts and buttons, no identifiers) or the home screen. **Settling** uses the panel's frame stream (helper `idle`): wait for the screen to start changing (`firstMs`, up to 500 ms after a tap: apps take a moment to react, and "quiet" before that means nothing), then until no more than 2 frames arrived in the last 150 ms (`quietFrames`: a caret blinking or a cell updating isn't an animation running); only then is the tree read. If a tap seems to have changed nothing, it settles once more and reads again. **Keyboard**: while a field has focus, an element below the keyboard (55% of the height) is first scrolled up into view and found again. Back: the navigation bar's back button when there is one, else an edge swipe. The `observe` / `tap` tools' own settle uses the same rule now.
- **Browser driver**: the `browser_*` machinery (`Browser::pilot_*` in web.rs): a snapshot remembered like an observe (its ids work for the caller's tools afterwards), click / type / press Enter / scroll / back, the DOM-quiet settle.

**Decision log** (`pilot/dataset.rs`), kept for training a local pilot later: every decision of every run is one JSON line in `<pilot folder>/<project hash>.decisions.jsonl`, next to the muscle memory. A record (`Record`, `v: 1`): `ts`, `run`, `step`, `target`, `app` / `url`, `goal`, `input_keys`, `checks`, `screen` (`summary`: the compact screen as the decider saw it; `candidates`: the typed candidate list with ids), `prev` (the previous action key, `start` first), `history`, `decider` (`memory`, `haiku`, `checks` when the success checks held — the `done` label a done-detector needs —, or `caller`: the calling agent's first device action after a `stuck` / `surprised` run, matched to a candidate by element id, scroll direction, back or Enter), `chosen`, `action`, `decision_ms`, then the run's `outcome`, `verified` and `on_success_path` (the step is on the path to `done`; no-op steps aren't; `null` for the caller's choice). Records are written when the run ends. **Privacy**: a text field's or masked field's contents are never stored (`<filled>`); each input value of 3+ characters is replaced by `<key>` wherever it shows (labels, page text, the goal, the URL, case-insensitive for ASCII); anything shaped like an API key (`sk-…`, 20+ chars) becomes `<redacted>`; no screenshots; local only, nothing uploads it. **Cap**: a project's file rotates to `.decisions.1.jsonl` at 20 MB (replacing the older one), and nothing is written while the folder's logs hold over 200 MB. **Settings > Devices > Device pilot**: "Save pilot decisions for training" (on by default; `pilot_log` in the backend settings), the folder and size, "Reveal in Finder" and "Delete" (with a confirm; the muscle memory stays). **Eval**: `dataset::eval(records, scorer)` is the spike's per-step accuracy (labelled states are the steps on a successful path; gold is the id chosen there), and `coool --coool-pilot-eval <file>` prints a log's records, labelled states, an always-first-action baseline and each logged decider's on-path rate. No training is built.

`COOOL_PILOT_DEBUG=1` prints each screen the pilot reads, with its signature, on stderr.

**In the chat** (`lib/pilot.ts`, `PilotRun` in `Chat.tsx`): a `pilot_run` call is one step, "Pilot · iPhone" (or Browser) with the goal, and under it the pilot's own steps as they happen (`pilot-progress` events `{ chat, run, started, end, outcome }` after each step), each with its decider (`memory` / `haiku` chip) and its time (perceive + decide + act + settle in the tooltip), then the ending: `done · verified · 2 steps · 6.5 s · 2 memory`, or the reason. Afterwards the tool result's JSON has the whole run, so a reopened chat shows the same. **Indicators**: a run ends with an `end` activity (`sim-activity` / `browser-activity` kind `end`), which turns the iPhone panel's "Agent is driving" pill, the header's dot and the Browser panel's "Agent" pill and tab mark off at once; they also go off when the chat's turn ends (they used to linger up to 3 s after the agent's last action).

**Tree reads.** The spike's 0.3–1.0 s (3.5 s on the Contacts edit sheet) was WebDriverAgent's `/source`; coool's own helper reads the same screens in 15–60 ms warm, so the read was never the bottleneck here. Measured on Settings / General / Contacts (13–26 elements): serial 20–55 ms, the new per-level pipelining (every request of a tree level in flight at once) 19–53 ms: no measurable gain, the bridge answers one at a time; `visibleOnly` cuts long lists. What is slow is the **first read of a freshly launched app**, 0.5–1.1 s (its accessibility server warming up, ~1–2 s after launch during which only the status bar answers), and settling: a navigation push settled in ~1.1–1.4 s with "no frame for 150 ms" (cells and indicators keep presenting frames now and then after the animation), ~0.7–0.9 s with `quietFrames`.

**Measured** (self-tests `pilot-iphone` and `pilot-browser`: a real Claude Haiku chat calls `pilot_run`, twice; Apple silicon, iOS 27.0 simulator):

The checks verified `done` every time and the harness confirmed the screen itself (the simulator's own tree; the page's own reports). A Haiku decision costs ~$0.0001 (1.1–1.4k input tokens, ~60% from the prompt cache after the first); the four runs cost $0.00075. On the iPhone a step is now mostly the device: ~0.5–1 s settle across a navigation push, 20–170 ms to read the tree.

**Self-tests**: `COOOL_SELFTEST=pilot-iphone,quit` (its own simulator, deleted after) and `pilot-browser,quit` (the `agent-browser` form) check the outcome, the screen or page state, the reply, the live steps in the chat, that the second run is mostly memory (and faster on the iPhone), and that "Agent is driving" / the "Agent" pill are off when the turn ends. `pilot-iphone` also checks that the second run is a warm start under 3.5 s, that the decision log holds both runs (Haiku then memory, each ending with `checks`, all on the successful path), and that Settings > Device pilot shows the log's folder and size; `pilot-browser` that the log holds the form's decisions with input keys and no typed value. Headless (`--coool-device-serve`, a warm simulator) the variants measured: in front on About 1.9–2.5 s; in front on the first screen 2.3–2.8 s; in the background on About (brought to front, back) 4.0 s; in front on an unknown screen, relaunched, 5.1–6.6 s.

**Known limits.** Some controls aren't in the accessibility tree the helper reads (the Contacts "New Contact" sheet's Cancel / Done buttons), so the pilot can't tap them. The keyboard's top is an estimate (no keyboard frame in the tree). Muscle memory is exact-match only: a screen whose visible text changes between runs (a clock, a count) misses and falls back to Haiku. Sliders, pickers and `<select>` aren't candidates yet.

## Mac panel (sandbox VM)

Phase 2 of the device panel: a **sandboxed Mac** behind the chat header's Mac button, so agents (and the person) use and test Mac apps in a macOS virtual machine shown in the right panel, never on the person's own desktop. It works like the iPhone panel: one shared device the panel shows and the chat's agent drives through `mac_*` tools in the same `coool-device` MCP server, with the same "Agent is driving" marks (`sim-activity` events with `udid: "mac"`).

### Design

- **The VM** (`app/src-tauri/native/coool-vm.m`, built by build.rs into OUT_DIR and embedded): a host helper process on Apple's Virtualization.framework, one per VM folder, speaking the coool-sim protocol (JSON lines in; framed JSON and JPEG frames out), so `device/helper.rs` drives it. It runs with `NSApplicationActivationPolicyProhibited`: no Dock icon, no menu bar, never active, and its one window is never put on screen, so nothing outside coool appears or takes focus. Guest: 4 CPUs, 6 GB, a 40 GB sparse raw disk (only written blocks take space), a 1280x800 display at 1x, a network device per the network setting (NAT, host-only or none; see "Security"), a USB keyboard, a screen-coordinate pointer and a trackpad, virtio-vsock, a memory balloon, and one shared folder.
- **The entitlement.** Only the helper needs `com.apple.security.virtualization`. build.rs signs it ad-hoc with `native/coool-vm.entitlements` right after compiling it; the signature lives inside the Mach-O, so the copy the app writes to `<data>/bin/coool-vm-<hash>` stays signed, in `tauri dev`, a debug build and a bundle alike. The app itself is not re-signed and needs no entitlement. (A notarized release would sign the helper with the Developer ID and the same entitlement.)
- **Install** (`mac_install`, the panel's Install button): the helper asks Apple for the latest restore image this Mac supports (`VZMacOSRestoreImage.fetchLatestSupported`), then downloads only what a virtual Mac's erase install reads, with HTTP range requests into a pruned `.ipsw`: the zip's central directory, its BuildManifest, the `vma2macosap` erase identities (the install and "macOS Customer", which personalizes recoveryOS) and every small file; it drops the other Macs' kernel caches and firmware and the Rosetta cryptex (5.6 GB, only for Intel apps). macOS 27.2.1: 16.5 GB instead of 25.6 GB. It refuses to start unless the download plus the install (~19 GB) plus a 6 GB margin fit on disk. `VZMacOSInstaller` installs it (about 5 minutes here), and the download is deleted as soon as the install succeeds. Everything lives in `<app local data>/vm` (`~/Library/Application Support/sh.coool.app/vm`; `COOOL_VM_DIR` overrides): `disk.img`, `aux.img`, `config.json` (hardware model, machine id, MAC address, OS, agent version), `guest.json` (0600), `ssh/` and `Shared/`. A `lock` file (flock) lets one coool drive the VM at a time; another gets "This Mac is in use by another coool".
- **First boot without hands** (`device/vm.rs`): macOS 27's guest provisioning (`VZMacGuestProvisioningOptions`) creates the account (`coool`, a random 24-character password kept in `guest.json`), logs it in automatically and turns on Remote Login: no Setup Assistant. coool then finds the guest's address in the NAT's DHCP leases (by its MAC address), and over SSH (password via `SSH_ASKPASS` from the environment, then a guest-only ed25519 key; `-F /dev/null`, `IdentityAgent=none`, no forwarding, its own known_hosts) installs the guest agent and settles the guest for automation: no sleep, no screen lock, no automatic macOS updates, no autocorrect or smart quotes (typing types exactly), and a sudoers rule for `/sbin/shutdown` only.
- **The guest agent** (`native/coool-vm-agent.m`, installed as `~/Library/Application Support/coool/coool agent.app`, a LaunchAgent in the logged-in session): listens on vsock port 7333, which only the host reaches (nothing on the network), and answers the frontmost app's accessibility tree (its windows, sheets and menu bar; breadth-first nodes in the coool-sim format so `observe.rs` renders them; ruler markers and scroll bars left out), launch / quit / list apps, open a URL or file, the pasteboard, and running a command. It is signed ad-hoc in the guest with a designated requirement on its bundle id alone, so the Accessibility grant (TCC keys on that requirement) survives agent updates; an install signed by hash is reset and granted again. The LaunchAgent's program is `/bin/sh -c 'exec "$0"' <agent>`: macOS's Background Task Management keys a launch item on its program's code signature and, at the next login after it changes, posts a new "App Background Activity: … can run in the background" alert, which stays on screen across restarts until it is closed. When the agent ran itself, every agent build (a new ad-hoc cdhash) added one: the Mac showed six stacked in every screenshot. sh's signature doesn't change with ours (`mac-btm-resign`: a re-signed agent and a reboot bring no alert). Each boot the agent also closes any such alert about itself (`dismissNotifications`: Notification Center's own Close action on alerts whose text names `coool-vm-agent` / `coool agent`; once before the boot returns, then a few times over the next 15 s, as macOS restores them a moment after login), so the setup's own alert and the old ones are gone before anyone looks. Self-test `mac-clean-boot`: a boot from shut down, the guest's screen read (OCR) at 0, 5, 12 and 20 s: no alert.
- **The Accessibility grant**, the one permission the agent needs, which macOS lets only real input switch on: coool does what a person would, with the VM's own keyboard and pointer, reading the screen with Vision OCR in the helper. It has the agent ask once, opens Privacy & Security > Accessibility ("Device Control and Data Access" on macOS 27), swipes away the "App Background Activity" banners that can cover the row (the agent can't close them yet: it has no Accessibility), finds the "coool agent" row, finds its switch in the picture (`switchIn`: the rightmost control-sized cluster in the row; on = accent colour), clicks it, types the guest password into the sheet, and confirms through the agent. On this Mac the whole first-run setup (SSH install + grant) took 30 s after boot. The setup reruns only when the agent's version changes.
- **Frames.** Virtualization.framework hands a display's frames only to a `VZVirtualMachineView` (its private screenshot call traps the VM service without one). The helper keeps one in a borderless window it never orders on screen and hooks `_VZFramebufferView presenter:didUpdateFrame:` (calling through): after each frame the view's layer holds the frame's IOSurface. Each new frame is JPEG-encoded and streamed (at most 15 fps, only when the screen changes, the current frame at once for a new subscriber); `screenshot` is ~10 ms; `idle` (the tools' settle) counts frames.
- **Input** is the VM's own hardware: the private `_VZKeyboard sendKeyEvents:` (macOS virtual key codes) and `_VZScreenCoordinatePointingDevice sendPointerEvents:` (the display's unit square, origin top left), plus scroll-wheel events, all on the VM's queue. The guest sees real HID input, so clicking and typing need no guest permission. Text a US keyboard can't type is pasted through the agent's pasteboard.
- **Shut down**: through the agent (`sudo -n /sbin/shutdown -h now`; the power button only shows macOS's "Are you sure?"), else the power button, forced off after the timeout. Quitting coool closes the helper's stdin; the helper shuts the guest down first (it waits for that stop's own reply, not any reply).
- **Staying truthful across boots.** "The Mac isn't running" while it ran, or after a shut down and boot in one session, came from three things, all fixed: (1) the helper crashed reading the last frame's IOSurface after the VM that made it had stopped (the surface dies with the VM's process; the crash took the next VM down with it). The helper now forgets the frame and detaches its view when a VM stops, takes frames only from the running VM's own view, and never reads a surface unless that VM runs and no stop is under way. (2) coool's "the agent answered" flag outlived the VM: it is now cleared by the helper's own word (any state but running, the helper exiting, a new helper), so a call after the guest shut itself down, crashed, or the helper restarted boots it again instead of trusting a Mac that is gone. (3) A stop callback about an earlier boot's VM, or a guest agent connection opened on an earlier boot, could act on the next one: callbacks are matched to their VM, a stop acts only on the VM it was asked about, and the agent connection is tied to the VM generation it was opened on. The helper's `status` reports "stopped" when its VM object no longer runs, whatever the last event said; a boot that finds the Mac stopping waits for that to finish. A `mac_*` tool that finds the Mac gone mid-call says so ("The sandbox Mac is off … call any mac_* tool again, or mac_device boot"), and is retried once when the Mac in fact still runs and the request never reached it. The panel reads the state again when its input or screen finds the Mac gone. coool's stderr logs each VM state change and why a VM stopped when coool didn't stop it. Self-tests: `mac-cycles` (ten shutdown → boot cycles in one session: the panel's Shut down and Boot, a shutdown from inside the guest, a restarted helper, a tool call that finds the Mac off, calls racing a boot, the guest agent restarted by launchd; after each an agent tool, the panel's input, a screenshot and the panel's screen all work, and while off the panel offers Boot) and `mac-idle` (ten minutes untouched, then the same checks).
- **Click wallpaper to reveal desktop** is set to "Only in Stage Manager" inside the guest (`com.apple.WindowManager EnableStandardClickToShowDesktop` false, the window manager restarted only when it changes): on macOS 27 a click on the empty desktop otherwise slides every window off screen, which confused agents and the pilot. Part of the first-run setup and checked at every boot, so a guest set up earlier gets it too. `mac-cycles` checks it with a control: with the setting on, a click at the desktop's corner left 3 of 15 words of the windows on screen; off, 15 of 15.

### The panel (`components/MacPanel.tsx`)

The Mac button toggles it like the other panel kinds (`rightPanel[key] = "mac"`, at least 740 px panes, resizable, width in localStorage `coool.macWidth`). Header: state pill (Not installed / Downloading n% / Installing n% / Off / Starting / Setting up: step / Running), the macOS version, Install (asks first: about 16 GB download, about 40 GB free; shows free space), Boot / Shut down, the network mark (globe / globe around a house / crossed-out globe, with a tooltip: what the Mac can reach now, and a setting that lands at the next boot), and an info popover (CPUs, memory, disk used, the network switch with its one line of plain truth, the shared folder path). `mac_network({ mode? })` reads or sets the network (`{ network, networkNow, applies: now|next boot, truth }`); `mac_status` carries `network` and `networkNow`; `mac-state` sends `networkNow` when it changes live. Body: the live screen, letterboxed; mouse (move, buttons, right click, wheel) and keyboard pass straight through while the screen has focus (a ring and a "Keyboard goes to the Mac · Release" chip; Escape goes to the guest; app shortcuts are suppressed for `data-key-capture`; held keys are released on blur). Input goes out in order: one `mac_input` call at a time, carrying what came in while the previous one was in flight (the command runs on a thread per call, so two calls in flight reached the Mac in either order: a key typed right after a click could arrive while the button was still down, or its up before its down, and was lost). Self-test `mac-click-type`: ten trusted clicks into TextEdit, each with a word typed in the same instant, every word whole and in order. ⌘V pastes the host clipboard as text. Commands: `mac_status`, `mac_install`, `mac_boot`, `mac_shutdown`, `mac_attach` (frames on a Channel), `mac_detach`, `mac_input`, `mac_bind`; event `mac-state` (state, progress, setup step, error).

### Agent tools (`mac_*` in `coool-device`)

`mac_observe` (the tree as `[id] role "label" value=… (x,y wxh)` in screen points, ids stable as on the iPhone; `screenshot: true` adds a JPEG), `mac_click` (id or point; `count`, `button: right`), `mac_type` (`into` an element replaces its contents: click, ⌘A, type; `submit`), `mac_press` (keys and shortcuts), `mac_scroll`, `mac_app` (launch by name, bundle id or path; quit; list; open), `mac_wait_for`, `mac_screenshot`, `mac_batch`, `mac_shell` (a command inside the Mac), `mac_share` (copies a host file or folder, e.g. an `.app` build, into the shared folder: clone on APFS; returns `/Volumes/My Shared Files/<name>`), `mac_device` (status, boot, shutdown). Every action returns the settled screen. The first call boots the Mac. `pilot_run` takes `target: "mac"` (`app` launches first; without it, `launch` candidates open the app the goal names; set_text clicks then replaces; back is ⌘[). Self-test `pilot-mac-direct` calls `pilot_run` directly (`selftest_pilot`, the gate included, no chat model): three Calculator goals and three TextEdit goals (type a sentence into a new document), each in its own wording so Claude Haiku decides; each ends `done`, verified, with Calculator in front / the sentence in the document (Haiku picks `launch` first).

### Security

- The guest sees one host folder: `<data>/vm/Shared` (virtiofs, automounted at `/Volumes/My Shared Files`). Nothing else of the host's file system, no home folder.
- No host credentials go in: the guest account's password is generated for the VM, the SSH key is a guest-only key made for it, ssh runs with no agent, no forwarding and no host config; the agent's vsock port isn't on any network.
- Tokens: as with the other tools, each chat's token maps to that chat only, and its `mac_*` calls act on the device bound to it; there is one Mac, shared by every chat that uses it (as the person's screen is), and the `mac_*` tools never reach the iPhone or Browser panel.
- **Network** (Settings > Devices > Mac, and the panel's info popover): **On** (default; NAT: the internet and this computer's network services), **Local** ("this computer only": a host-only vmnet network with no NAT and no DNS proxy, so the guest reaches this Mac, e.g. a dev server here, and nothing beyond), **Off** (no network device in the VM at all). The header shows it at all times: a globe (On), a globe around a house (Local), a crossed-out globe (Off), with a tooltip saying what the Mac can reach. The one line of plain truth under the switch: On, "The Mac reaches the internet and this computer's network services. Anything in its shared folder can leave this computer."; Local, "…only this computer…, not the internet"; Off, "…no network at all: nothing in it, or in its shared folder, can leave through it". When it applies: the setting is saved in the VM's `config.json` (`network`) for the next boot; while the Mac runs with a network device (booted On or Local) a change applies at once (the device's attachment is swapped live; Off detaches it, like pulling the cable); a Mac booted Off has no device, so On or Local applies at the next boot (the switch says so). coool's own tools don't need the network: the guest agent talks over vsock. Only coool's one-time setup (the first boot, or an agent update) reaches the guest over SSH: with the network Off that one boot gets the Local network and is unplugged as soon as setup is done, so the guest never reaches the internet. Host-only needs macOS 26 on this Mac (vmnet's `vmnet_network_create`, which works with the virtualization entitlement alone). Local is not a firewall: the guest can reach every service on this Mac that listens on all interfaces.

### Numbers (this Mac: Apple silicon, 24 GB, macOS 27.0.1 host, macOS 27.2.1 guest)

Download 16.5 GB in ~8 min; install 274 s; disk.img 40 GB logical, ~20 GB used after install, ~24 GB after setup. Boot to the agent answering: 15.7–18 s (cold, set up); first boot with provisioning and setup ~80 s. Guest RAM 6 GB. Tool calls in the `agent-mac` run: `mac_app` launch 1.0 s, `mac_type` (40 characters) 1.1 s, `mac_observe` <0.1 s, screenshot ~10 ms.

**Self-test**: `COOOL_SELFTEST=agent-mac,quit` reuses the installed base Mac (it never installs one): boots it, opens a Haiku chat's Mac panel, asks the agent to launch TextEdit, type a sentence and read it back, then checks the document through the backend's own read of the Mac (`selftest_mac_screen`) and the reply, with screenshots, and closes TextEdit unsaved (`selftest_mac`). `COOOL_VM_DEBUG=1` saves the setup's screenshots and OCR to the VM folder.

**Limits.** Apple silicon and a macOS 27 host for the automatic first boot (older hosts can't provision the guest). The frame source and input use private Virtualization.framework methods (selectors looked up at runtime; nothing links privately) and the Accessibility grant reads System Settings' layout, so a macOS update may need adjusting both. No Rosetta in the guest (Intel-only apps won't run). One VM; no snapshots or save/restore yet (a saved state would cost about 6 GB of disk). The guest's clock follows its own time zone (Pacific by default).

## Agent presence

When an agent acts in a device panel (Browser, iPhone, sandbox Mac), the person sees it the way they would watch a collaborator: a cursor glides to each action's target before it lands, with a small label saying who acts and what it is doing, typed text arrives in the field, and a soft beam runs around the panel's frame while it drives. The cursor and label are coool's own design (palette and type, no library); the beam is libraries.dev's Border Beam, at the owner's request.

**Who acts** (`device/presence.rs`). An actor is one MCP connection of a chat (each connection is served on its own thread: a sub-agent that connects on its own is a second actor) or one `pilot_run` of a chat. The thread-local actor is stamped on every activity event: `actor` (`<chat>:c<conn>` or `<chat>:p<run>`), `by` (`agent` / `pilot`), `decider` (a pilot step's `memory` / `haiku`, set by the run before it acts) and `provider` (the chat's, recorded when coool starts it: `McpFor` now gets the provider). The pilot also says when its decider is choosing (`think`) and when its run ends (`end`) on all three targets.

**Events, early enough.** `sim-activity` (iPhone; the Mac as `udid: "mac"`) is sent just before the action starts, with its target point (`x`,`y`; a swipe or scroll on to `x2`,`y2`), `label` (what it acts on: the element's name, the key, the scroll direction), `text` for typing (dots when the field looks secret) and, for typing, the field's point (the `into` target, or the focused field of the last screen read). The panel maps device coordinates (points, guest pixels) onto the scaled screen. Nothing waits for the cursor on the iPhone and the Mac: the action lands as it always did, and the frame stream's own latency (tens of ms) plus a quick glide keep the cursor arriving with the effect.

**The Browser panel** is a native webview above the app's HTML, so the page script (`web_agent.js`) draws its cursors itself: each action's command carries `presence` (`{actor, name, mark, tint, decider, from, reduce, defer}`); everything lives in one fixed, click-through host with a closed shadow root, styled through the CSSOM and animated with the Web Animations API (a strict CSP doesn't stop it), left out of snapshots and of the idle signal. A click waits `defer` (50 ms) for the cursor on its way and `idle` reports it `pending`, so the tools' settle waits for it: the only added latency, per click, and only when the cursor actually travels. Typing sets the value at once (as before) and covers the field's new text with a copy in the field's own font and colour that reveals it a character at a time behind a tinted caret (only over a solid background; else the label alone). The cursor's last point is kept per actor so a new page starts it there; `browser_presence_end(chat)` (the frontend, when the chat's turn ends) and a pilot's end rest it, then fade it. The beam's box is the page area, and the native view sits 4 px inside it (`PAGE_INSET`), so the beam's edge shows in that gutter around the page.

**Cursor and label** (`components/Presence.tsx`, `lib/presence.ts`, words in `lib/presenceWords.ts`). The arrow is coool's own (rounded, tinted fill, white edge, soft shadow); the label is a two-line tinted pill: who (the provider's mark in a white chip and its name, or the pilot glyph and "Pilot · memory" / "Pilot · Haiku") over what ("Tapping General", "Clicking Add cup", "Typing the email", "Typing in Untitled", "Scrolling down", "Pressing Return", "Reading the screen", "Haiku is choosing"; "Thinking" after 1.8 s without an action). Glides take 160–340 ms by distance on `cubic-bezier(0.22, 0.75, 0.2, 1)` (quick out, calm landing, no overshoot); a tap or click ends in a press ring; a swipe glides to its start, then drags; the label changes side near an edge once the cursor has arrived. A run ends on the pilot's `end`, the chat's turn ending, or 12 s with no action: the cursor rests 900 ms, then fades in 420 ms. Each actor keeps its tint while shown: `--presence-0` (the running blue), `--presence-1` (indigo), `--presence-2` (teal); two chats on the shared Mac show two cursors.

**The beam** (`PanelBeam`): libraries.dev's Border Beam, the `border-beam` package (MIT, no runtime dependencies, pinned to exactly 1.4.1; its shipped source was read before adding it: it only renders, with an inline `<style>`, CSS animations, `matchMedia` and resize / intersection observers; no network, storage or eval, no install script), at the look its site shows by default: `BEAM = { size: "md", colorVariant: "colorful", strength: 0.7 }` in `components/Presence.tsx` (the one place to change size, colours or strength). It is an overlay over each panel's frame (the iPhone's screen, the Mac's screen, the Browser's page area) and draws on the frame's edge: a 4 px travelling line (`BEAM_LINE`), set 1.5 px into a dark 7 px bezel around the iPhone and the Mac so it has dark on both sides in either theme (the Browser's gutter goes dark while it runs), white at its head and blue to pink along its tail (`beamCss` replaces the package's stroke, a white band at most 75 % with its colours in a few fixed spots: around a device it read as a faint glow at one corner), and the package's soft inner glow, hue-shifting; `theme` follows coool's theme, `active` is true only while an agent drives that panel (it fades in with the first action and out about half a second after the last actor rests). The frames' hairline edge is drawn inset, since the wrapper clips. It replaces the old "Agent is driving" pills (the label says more); the Browser tab's blue dot stays (it says which tab).

**Reduced motion** (`useMotion`, `.reduce-motion`; the frontend tells the backend with `presence_motion` for the page cursors): no glide (the cursor is placed), no press ring or typing reveal, the animated beam isn't mounted at all (no CSS animation runs; before, its fade-out and hue shift kept running) and a static 2 px ring in the actor's tint shows while it drives, with the label. The frame and the screen inside it stay the same elements when motion changes (Auto changes it as the machine gets busy), so nothing remounts.

**Mock** (`?presence=iphone|mac|browser`, `lib/mockPresence.ts`): a scripted agent loops through each panel (a drawn Settings app with a rename and a pilot hand-off; two chats on the Mac at once; the coffee form in a framed page that runs the real page script, then the pilot replaying it from memory).

**Self-tests**: `agent-browser`, `agent-iphone`, `agent-mac`, `pilot-iphone`, `pilot-browser` check that the cursor (with its label; "Pilot · memory|Haiku" for the pilot) and the beam show while the agent acts, take a screenshot mid-action, and that both clear after the turn (`selftest_page_cursors` reads the page's own cursors); they log each tool's `act / settle / observe` ms (`ACT` lines). The click outline and press ring are drawn only while their element is on the page: not at all when the click removed it before the cursor arrived, and taken down within 50 ms when it leaves or stops showing (a banner fading out). `browser-settle` (no model; `COOOL_SELFTEST_SITE` names a local site with a client-rendered page, a page that never stops changing, a long `content-visibility: auto` page and a banner whose buttons remove themselves) drives the tools directly (`selftest_browser_tool`) and logs `TIMING` lines; `browser-real` opens four public affectui.com component pages the same way, saves the first screenshot after each navigation and logs Reduce motion and the beam.

## Device permissions

The `coool-device` tools are callable without the CLI's own prompt (see the MCP server above). Whether a call may go ahead is decided by **coool's permission gate** in the server (`device/gate.rs`), so it works the same for Claude and Codex and doesn't depend on either CLI's prompt. A call the gate holds shows a **permission request in its chat through the usual request UI** (the approval card, "Needs you" in the sidebar, tabs and Mission control, Mission control's Allow / Deny, the notification), and then continues, or returns "Denied by the person: … coool did not do it; don't try another way around" to the agent. No answer within 5 minutes is a denial (the card is taken back with a note in the chat); the turn ending (Stop, an exit) cancels it. The person's own clicks and typing in a panel never pass the gate.

**Modes.** The gate follows the chat's permission mode (`ready.permission_mode`):

| CLI | asks (the rules below) | doesn't ask | denies what would ask |
|---|---|---|---|
| Claude Code | `default` (Ask), `acceptEdits` (it still asks before commands), `plan` | `bypassPermissions`, `auto` | `dontAsk` |
| Codex (approval policy) | `untrusted`, `on-request`, `on-failure` | `never` (also what "Full access" sets) | — |

An unknown or not yet reported mode asks. A chat coool didn't start (the headless `--coool-device-serve`, the self-test's scripted client) has no gate.

**The rules** (in an asking mode):

| what | asks | its card says | can be remembered |
|---|---|---|---|
| reading: `observe`, screenshots, `wait_for`, `browser_tabs list`, `app list`, `device status/list`, `mac_device status`, scrolling in the Browser or the Mac | never | — | — |
| the first change on a device in a chat (a tap, a click, typing, a key, launching an app, booting, …) | once per chat per device | "use the Browser / the iPhone / the sandbox Mac", what it is about to do ("Tap “General”", "Open http://127.0.0.1:18765/form") | once · this chat · always in this project |
| Browser: an action on, or a navigation to, a site not yet allowed in this chat (registrable domain: `www.example.co.uk` → `example.co.uk`; `user.github.io` and other hosting platforms per subdomain; an IP or `localhost` as itself). Pages where the person is signed in are covered by this rule. | each new site | "open example.com" (with the first-use card when both apply: "Allow the Browser and example.com in this chat") | once · this chat · always in this project (the project's site list) |
| Browser: a click, Enter or Space that submits a form (a submit button of a form, Enter in a form's field, `browser_type` with `submit`) | always | "submit a form: Press “Sign in” on example.com" | once only |
| Browser: typing into a password field (type=password, autocomplete current/new-password, one-time-code) or a payment field (autocomplete `cc-*`, names like card number, CVC, IBAN) | always | "type a password: Into “Password” on example.com" / "type into a payment field" | once only |
| Mac: `mac_shell` | always | "run a command in the sandbox Mac", the command | once only |
| Mac: launching or opening something from the shared folder (`mac_app` launch/open, a `mac_batch` launch, under `/Volumes/My Shared Files`) | always | "open something from the shared folder", the path | once only |
| Mac: `mac_share` of a path outside the chat's project folder | always | "copy a file into the sandbox Mac", the path, and that the shared folder can leave while the network is on | once only |
| iPhone: `app install` | always | "install an app on the iPhone", the path | once only |
| `pilot_run` | once for the run | "run the pilot on the Browser", the goal and where it starts; its own steps then don't ask one by one, but the always-ask kinds and new sites still stop the run and ask (denied: the run ends `stuck` with the denial as its reason) | once only |

"This chat" lasts while coool runs. "Always in this project" is kept in coool's own data (`<app local data>/device-grants.json`, by project folder; nothing in the project, nothing in the CLIs' settings) and never covers the always-ask kinds, except the Browser's site list the person builds up. **Settings > Devices > Agent permissions** lists each project's devices and sites, each removable, and "Revoke all". The iPhone has no erase or delete tool for agents (only the person, in Settings > Devices), so there is nothing of that kind to gate.

**How the Browser knows.** Before a click / type / select / press in an asking mode, the page script's `inspect` op (read-only, in coool's content world) reports whether the action would submit a form (and the submit button's label), whether the field is a password or payment field (and its name), where a link goes, and the page's URL. Forms submitted only by a page's own JavaScript (a `<div>` with a click handler that posts) aren't recognised as submits: they fall under the site rule.

**The request** (`coool_core::chat::ChatHandle::ask`, CHAT_SPEC "Requests of coool's own"): `permission_request` with `tool` "Browser" / "iPhone" / "Mac", `summary` "Browser · Press “Submit order” on 127.0.0.1", `input.coool_device = { device, kind: use|site|submit|secret|shell|launch|share|install|pilot, lead, body, note }`, and `remember` options `chat` ("Allow the Browser in this chat") and `project` ("Always allow the Browser in this project", `file` "coool (Settings > Devices)", shown as "Saved in coool"). The card's title is "Claude wants to <lead>", its body the exact what and where.

**Cost.** In a mode that doesn't ask, and for every read, the gate is one mode lookup (`gate_asks`: the chat's handle and its mode string), under 50 µs per call (asserted over 10,000 checks in the unit test), nothing measurable next to the tools' `act` timings (milliseconds). In an asking mode, an allowed action adds that lookup plus, in the Browser, one `inspect` evaluation (about as cheap as an `observe` of one element, ~1–2 ms).

**Self-tests**: `gate-browser` / `gate-browser-codex` (a chat in `default` / `on-request` mode opens the form: using the Browser asks once with the site, "this chat"; the submit stops and asks with its label and the site, "Needs you" shows, Allow submits; a second turn's submit is denied: the agent gets the denial, the page gets nothing) and `gate-mac` / `gate-mac-codex` (`mac_shell` stops and asks showing the command; Allow runs it (the harness reads the file in the guest), Deny doesn't (the file is absent)). `mac-network` (no model calls) boots the Mac Off (no `en0`, no default route, no DNS, `curl https://example.com` fails, coool's screen read works), then Local (en0 gets 192.168.128.x from vmnet's DHCP within a few seconds of the agent answering, the host at .1 answers ping, 1.1.1.1 and example.com don't), switches it to On live (example.com answers within seconds), and leaves it shut down and On. The other agent scenarios answer the gate as they go ("this chat" for using a device or a site, Allow once for the rest) and log each request (`ASK` lines).

## Engineering constraints

- The frontend must also run in a plain browser (`pnpm dev`) with a built-in mock data source when Tauri is absent: realistic sessions that change over time (statuses flipping, steps arriving, a fake terminal stream). This is how the UI gets developed and screenshot-tested without the shell, and it is the demo for coool.sh later.
- Keep state in one small store (Zustand or a reducer); events are the only source of truth for sessions.
- Lists must stay smooth with 50 sessions and 300 activity rows each (virtualise the timeline if needed).
- Terminal: one xterm instance per open managed session, kept alive when its tab is hidden; fit on resize and send `pty_resize`.
- macOS first (overlay title bar with traffic lights inset into the sidebar, draggable region), but nothing that prevents Linux/Windows later.
- **Frosted glass** (`lib/glass.ts`, `lib/glassHoles.ts`, `app/src-tauri/src/glass.rs`): real macOS vibrancy in two places, the window chrome (title bar with the tabs, and the icon rail: the `bg-chrome` surface the sheet lies on) and the background of the device panels (iPhone, Mac, Browser: the right panel's frame for those kinds, `bg-side-glass`; Jobs and Models stay solid). Everything else stays opaque. Native side: `glass_set({ on, dark }) -> { active, reduce_transparency, supported }` puts one `NSVisualEffectView` under every webview of the main window (material Sidebar, blending behind-window, state follows the window's activity so an inactive window goes flat like Finder's sidebar, appearance VibrantLight / VibrantDark from the app's theme: a plain Aqua appearance would make it draw a flat fill), and makes the window non-opaque with a clear background; off hides the view and makes the window opaque again (the page then sets the solid `--panel` colour as before). Public AppKit only; the webview is already transparent because the window has a background colour (wry's `drawsBackground`, unchanged), so no `macOSPrivateApi`. Page side: `data-glass="on"` on <html> only once the view shows (off: the page goes solid first, then the window), turning `--window` transparent and `--chrome` / `--side-glass` into a tint of the solid colour (light 36% / 44%, dark 50% / 56%) with a firmer `--glass-line` hairline at the panels' edge. The device panels sit inside the opaque sheet, so the sheet's background is its own layer (`data-sheet-bg`) with holes masked where those panels are; the holes follow the panels on any resize of the sheet, a panel or its row, then for a few frames (springs, tab fades), and stop measuring once nothing moves. The Browser panel's toolbar and gutter are glass; its page is the native child webview above it, as before. Theme changes with glass on: the material changes first, then the page. **Fallback** to today's solid colours: the setting off, macOS **Reduce transparency** (read on every `glass_set`, and again whenever the window comes to the front; a debug build can force it with `COOOL_REDUCE_TRANSPARENCY=1`), the browser mock, or a backend without the command. Full screen keeps the glass (the wallpaper shows through). Cost measured in the real app (self-test `glass`, 1440×900, M-series): scrolling a 240-message chat and resizing the window keep the same frame pacing with it on and off; see the scenario's PERF lines.
